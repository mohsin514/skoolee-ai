# Durable workflow operations — SKO-382

Report publication commits its in-app notification intent in the same PostgreSQL transaction as the exam and report statuses. A Redis outage or process death cannot remove that intent. The HTTP result includes `workflowId` and `backgroundDelivery: pending`; publication itself is complete. School-facing workflow UI remains SKO-386. This is an operator runbook and API contract, not a new application console.

## Deploy and run

Apply `20261008022000_durable_outbox` through the existing reviewed migration gate. Do not regenerate the frozen baseline. Run `pnpm worker:outbox` as a separately supervised, long-lived Node process with `DATABASE_URL` and `REDIS_URL`; a serverless request is not a worker supervisor. Restart on unexpected exit. No new provider credentials are required. Run at least one instance; multiple instances are safe. The dispatcher scans every second; expired leases and lost Redis jobs are redelivered within approximately 60 seconds plus bounded retry delay.

The dispatcher must use a reviewed service database role able to scan workflow metadata across schools. Domain callbacks still scope every raw query by the event's school and bind transaction-local RLS context. If optional RLS is enabled, provision the service role deliberately; the ordinary restricted request role cannot perform cross-school dispatch. Never share a worker connection's session-level tenant setting. Additive ledger tables are included in the generated application tenant registry; raw orchestration queries explicitly scope their mutations.

Existing `ai-remarks`, `pdf-generation`, and `notifications` queue definitions have no application enqueue producers found in the inspected source. They are not silently redirected. ## Consumer contract

`appendEvent(tx, ...)` requires a stable school-scoped identity, actor ID, reference ID, kind, and version. Redis receives only event/school IDs. Names, marks, addresses, message bodies, attachments, and credentials stay in domain storage. Reusing an identity with different references is rejected. Event and initial job creation must use the **same transaction** as the domain write.

`consume` claims a fenced lease, binds fresh async tenant context, and limits a run to five attempts. Never write domain effects outside `ctx.effect(identity, transactionCallback)`: the job row lock, domain writes, unique receipt, and checkpoint commit atomically. A repeated effect skips its confirmed receipt. Resolve current access and source publication inside that callback. The report consumer checks active actor, current campus/role, current report-edit permissions, current school status, and current exam publication before resolving recipients. Queue input is not authorization.

Long operations receive heartbeats; an expired/replaced token cannot commit database effects. Crashes resume from committed effect receipts, not from an in-memory progress percentage. A handler's nontransactional computation may run again. External calls belong in `ctx.external(identity, authorize, send)`: intent becomes `uncertain` **before** the call, so loss of the response never permits automatic resend. This deliberately trades unattended recovery for avoiding unproven duplicate provider effects. A success receipt remains traceable even if cancellation arrived during the call.

Realtime inbox hints use the existing Redis pub/sub channel after the notification rows commit. They are best effort, like the existing implementation; inbox storage is authoritative and can be reloaded after reconnection. They are separate from durable queue payloads.

## Reconciliation and recovery

Use the existing authenticated APP_OWNER session with `GET /api/owner/workflows?schoolId=...`. Responses are private and `no-store`. The report returns up to 500 event/job summaries with orphaned/failed and unfinished work first, oldest first within each group. Add `eventId=...` to inspect a selected workflow regardless of the list limit. Fields include creation/dispatch/start/finish times, attempts and budget, checkpoint, cancellation request, safe reason, confirmed/uncertain-effect counts, event/pending age, next attempt and lease timestamps, and `orphaned`, `overdue`, `stuck`, `dead-letter`, or `tracked` classification. A running job with an absent lease is also stuck. It excludes domain payloads and student references. An empty scope returns `workflows: []`; database failure returns 503 and pending work remains stored. Only a currently active APP_OWNER may inspect or mutate workflows, regardless of stale session role claims.

Before a mutation, inspect the selected school/workflow, checkpoint and effects; state the intended boundary to the operator and choose a reason. Use same-origin `POST /api/owner/workflows` with `{ "schoolId": "...", "eventId": "...", "action": "retry", "reason": "TRANSIENT_FAILURE_RESOLVED" }` for a failed job after correcting its cause. Other allowed retry reasons are `CONFIGURATION_CORRECTED` and `AUTHORIZATION_RESTORED`. It grants five more attempts, preserves confirmed checkpoints, and writes actor, action, reason, prior state and checkpoint to the audit record. The execution-time policy still applies. Already running, completed, cancelled, or uncertain external work cannot be retried through this action. A success response means scheduled, not completed.

Use the same endpoint with `action: cancel` and reason `NO_LONGER_REQUIRED`, `INCORRECT_REQUEST`, or `INCIDENT_CONTAINMENT` to request the next safe boundary. Queued/retrying jobs stop immediately; an active transaction finishes or rolls back before cancellation takes effect. Completed jobs are not relabelled. Confirmed and uncertain effects are never deleted or marked undone. Missing/incompatible reasons or extra free-text fields return 400 without mutation. Cross-origin requests return 403. State conflicts return 409: reload the scoped report and reassess; never infer success from the click or blindly repeat a command. The API is the existing guarded operation; no modal is introduced by this infrastructure issue.

For `EXTERNAL_OUTCOME_UNCERTAIN`, stop and reconcile the provider's receipt or domain delivery identity with the responsible operator. Do not delete the receipt or press retry. Registered report and announcement adapters use the conservative external-effect contract. There is no automatic uncertainty-clearing command: operator retry refuses uncertain effects. A provider-specific, reviewed and audited resolution is needed before uncertain work can be replayed; this issue does not invent provider acceptance evidence.

The WhatsApp route verifies exact request bytes before parsing. Valid status receipts resolve a unique communication through the configured provider account and provider message ID, never a caller-supplied school. Event time must be at or after originating intent creation (provider-second precision) and at most five minutes in the future. UTC comparison does not depend on database session timezone. Receipt uniqueness is `(communication_id, state, occurred_at)`; signed out-of-order status history stays independent of cancellation. Duplicate callbacks are acknowledged without duplicate rows. Unknown/ambiguous/not-yet-sent origins return a generic retryable 500 instead of falsely acknowledging persistence; exact replay succeeds after origin visibility is repaired. Unowned accounts and malformed/invalid timestamp statuses do not mutate records. The provider account should be dedicated/configured to the adapter: unresolved origin errors need monitored operator follow-up. This is a bounded redelivery adapter, not an inbound durable inbox or a promise that the provider retries forever. Confirm the actual provider redelivery window and recovery/export procedure in the deployment runbook before activating live delivery; no provider-specific retry duration is assumed here.

Investigate `orphaned` records as ledger corruption (the normal atomic producer cannot create them). Investigate `stuck` leases beyond two scan cycles, old pending events, repeated `WORKER_FAILURE`, `ATTEMPTS_EXHAUSTED`, and failed authorization. Logs contain only static reason codes. Alert thresholds and continuous process supervision must be configured in the deployment environment; this PR does not provision production infrastructure.
