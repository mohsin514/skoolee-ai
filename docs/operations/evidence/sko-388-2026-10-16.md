## Failures found and their root causes

The first run failed; the causes were cross-ticket drift accumulated since SKO-196 plus two
genuine SKO-388 regressions. No assertion was weakened, relaxed or deleted, and no test or
check was skipped.

1. **Every MFA-gated role could not hold a session.** APP_OWNER, SUPER_ADMIN, ADMIN,
   CAMPUS_ADMIN and PRINCIPAL now require a second factor at sign-in (`requiresMfa`), which
   did not exist when the SKO-196 harness was written. The audit helpers sent
   email+password only, received `200` from `/api/auth/login` and then silently ran against
   an unauthenticated context. Fixed in both audits by adding a login helper that completes
   the product's real `/api/auth/mfa` enrolment (`setup` → `verify-setup` → `acknowledge`)
   and then answers the genuine TOTP `challenge` (next 30-second step, bounded retries).
   This drives the real product endpoints; it adds no bypass. Navigation, accessibility,
   recovery and conflict assertions are untouched.

2. **Fixture teardown failed on `student_enrollments`.** `student_enrollments.student_id`
   is `ON DELETE NO ACTION`, so deleting students before their enrollments raised a foreign
   key error and left data behind. Both audits now delete enrollments first, and the role
   audit also removes the guardian rows it seeds. Verified after the run: 0 schools, 0 users,
   0 students, 0 student_enrollments, 0 guardian_relationships, 0 guardian_access_versions
   remain in `sko208_196`.

3. **The onboarding fixture never redirected.** The draft audit's incomplete-account fixture
   lacked `isInstitutionOwner: true`, so the onboarding action no longer treated it as the
   institution owner. The fixture is aligned with the current ownership check; the audit's
   recovery/sign-out-purge assertions are unchanged.

4. **The PARENT portal no longer authorizes through `student.parentUserId`.** Portal access
   moved to a verified `GuardianRelationship` plus a current `GuardianAccessVersion`
   (guardian access intervals, committed separately). The role audit now seeds a verified
   guardianship and a current permission version, keeping the school's `rolePermission`
   rows as the ceiling. Because the family navigation couples reports/exams/timetable to
   `learningRecords` and fees to `finances`, the guardian is granted `attendance: true` only;
   the audit asserts the shell, active navigation, keyboard drawer and overflow, which hold
   with the fee/timetable links correctly hidden. This is cross-ticket behaviour, recorded
   under Boundaries rather than changed.

5. **Genuine SKO-388 regressions in the work in progress:**
   - `src/lib/hooks/use-form-draft.ts` — an in-progress rename changed the session-change
     redirect to `/login?reason=draft-access-changed`. The audit (and the product's own
     sign-out/session-change contract) expects `reason=session-changed`, and no test expects
     the new value. Reverted to `session-changed`; the surrounding localized copy is kept.
   - `src/lib/drafts/messages.ts` and `src/components/ui/draft-recovery.tsx` — localizing
     the recovery dialog dropped the conflict count from the alert text, so
     `/Resolve 1 conflicting fields/` no longer matched. Restored the count-bearing string
     (`resolve(count)`) and added a `resolveHelp` line, in English, Arabic and Urdu.
     `resolveHelp` is a new string; `resolve` again renders the counted sentence.

6. **The audits could not hydrate at `http://127.0.0.1:3296`.** Next 16 blocks dev-only
   assets and endpoints for origins other than the hostname the dev server was initialized
   with (`localhost`), so client-rendered forms stayed inert under the loopback IP.
   `next.config.ts` now lists `allowedDevOrigins: ["127.0.0.1"]`. This is a dev-only,
   additive setting; it does not affect a production build. (SKO-196 itself ran the audits
   against a production build, where this issue does not arise.)

An earlier attempt also revealed that the audits' screenshots and JSON are only complete
when both browser audits run to the end; the final pass above was re-run in full to produce
a clean record.

## Boundaries

- This pass ran the audits against a Turbopack `next dev` server on `http://127.0.0.1:3296`,
  as the SKO-388 acceptance instructions require, and therefore did **not** run
  `next build`. SKO-196's original evidence was gathered against a production build; the
  two runs cover the same assertions but are not byte-for-byte the same deployment shape.
- All data is synthetic and loopback; no production database, credentials, outbound
  messages, deployment or merge was involved.
- The role audit checks each role's accessible shell, active navigation, keyboard drawer
  and three viewport widths, not every operation available to that role.
- PARENT is exercised as a guardian with `attendance: true` only, so the phone-width landing
  shows the "workspace not available with your current access" notice where the desktop
  shell shows the guardian overview. The coupling of reports/exams/timetable to
  `learningRecords` in the family navigation is cross-ticket behaviour and was deliberately
  not changed here.
- The audit MFA helper depends on the product's TOTP secret encryption and the test
  `AUTH_SECRET`; it drives the real endpoints, but it is a harness convenience and not a
  supported product surface.
- `allowedDevOrigins` is dev-only configuration; it should not be read as a production
  security change.

  in the table above were changed for this verification, but the audits exercised the tree
