# SKO-394 [020] Permanent student identity and enrollment history — verification 16 October 2026

DB-only acceptance suite `tests/enrollment/domain.test.ts` (single test). Reported as 0/1
with a `PrismaClientKnownRequestError` that did not match `/Foreign key/`. Investigation
showed this was **not** Prisma error-text drift and **not** a product/schema defect: the
acceptance database had no fixture rows, so the delete matched a "record not found" error
instead of a foreign-key violation. Loading the documented fixture (the suite's required
precondition) restores the intended behaviour and the suite passes 1/1.

## Failing assertion

`tests/enrollment/domain.test.ts:13`

```ts
await assert.rejects(()=>db.student.delete({where:{id:"pupil-main"}}),/Foreign key/);
```

Observed input:

```
PrismaClientKnownRequestError:
An operation failed because it depends on one or more records that were required but
not found. No record was found for a delete.
```

This is Prisma `P2025` (record not found), not `P2003` (foreign-key constraint),
because `students.id = 'pupil-main'` did not exist.

## Root cause

1. The dedicated database `postgresql://angular_dev_15@127.0.0.1:55417/sko217` was
   migrated (51 rows in `_prisma_migrations`, 157 public tables) but **empty** —
   `select count(*) from students` returned `0` and `schools` returned `0`.
   Row-level security is not the cause: `relrowsecurity = relforcerowsecurity = false`
   on `students`/`schools`/`student_enrollments`/`invoices` and the connection user is the
   table owner.
2. The suite is not self-seeding. Per `docs/qa/SKO-217.md` ("Fresh domain/browser fixtures
   expect a newly migrated disposable `sko217` database"), `tests/enrollment/fixture.ts`
   must be loaded first. It had not been run in this environment.
3. With no `pupil-main` row, `delete` returns `P2025`, whose text does not contain
   "Foreign key", so the assertion fails — a misleading symptom that looks like wording
   drift.

After loading the fixture, the same delete is correctly blocked by a real constraint:

```
code: P2003
name: PrismaClientKnownRequestError
message: ... Foreign key constraint violated on the constraint: `student_enrollments_student_id_fkey`
matches /Foreign key/: true
row still exists: true
```

The constraint is the intended one, from
`prisma/migrations/20261008081700_student_enrollment/migration.sql`:

```sql
ALTER TABLE "student_enrollments"
  ADD CONSTRAINT "student_enrollments_student_id_fkey"
  FOREIGN KEY ("student_id") REFERENCES "students"("id")
  ON DELETE NO ACTION ON UPDATE CASCADE;
```

## Is the assertion brittle? No

- Prisma Client **6.19.3** still emits the phrase `Foreign key constraint violated ...`,
  so `/Foreign key/` matches on the correct path. No wording-drift workaround is needed.
- The underlying behaviour (a pupil with enrollment history cannot be deleted) is correct
  and enforced at the database level, independent of the application.
- Because there is no wording drift and no schema/product defect, the assertion was left
  exactly as written. Making no change avoids weakening or churning the acceptance check.

Decision: **no source, schema or migration change was required.** The only real defect was a
missing environment prerequisite (fixture data), which is a data-preparation step, not
application code.

## Boundaries

- No UI/browser verification was performed (the suite is DB-only and explicitly does not
  need an HTTP app). No `next dev` server was started or stopped and no `next build` was run.
- No repository `.env` was loaded; the database URL was supplied explicitly and the test
  asserts hostname `127.0.0.1`, port `55417`, database `sko217`.
- The fixture is synthetic; this proves constraint/trigger behaviour on synthetic data, not
  production records or hosted-database migration.
- Remaining uncertainty: the suite is stateful by design. If it is re-run without reloading
  `tests/enrollment/fixture.ts` on a fresh database, it fails on the later `applyEnrollment`
  steps (e.g. `/Attendance/` at line 19), not because of any code defect. Any harness that
  runs this suite must reset + reload the fixture first.
