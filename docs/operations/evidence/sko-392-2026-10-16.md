# SKO-392 [018] Language, RTL, timezone, calendar and currency — verification 16 October 2026

DB-only acceptance suite `tests/locale/database.test.ts` was 0/1. The pure locale
suites (`country`, `events`, `language-cookie`) already passed and were kept green.
The failure was a **cross-ticket authorization regression**: a guardian-target
guard added on 2026-10-13 (commit `0452cc7`) denied an institution-only notice
addressed to one parent, breaking the AC8a locale-snapshot check written on

## Root cause

`assertCommunicationTarget` (as introduced by `0452cc7`) had:

```ts
if (!target.studentId && !target.parentUserId) return;                     // line 32
if (!target.parentUserId && !target.recipient) throw new AccessDenied(...);// line 33
if (!(await authorizedGuardianCommunicationTargets(target, channel, permission)).length)
  throw new AccessDenied("communication", "send");                        // line 34
```

`authorizedGuardianCommunicationTargets` returns `[]` whenever `target.studentId`
is empty (line 11). So a target of `{ schoolId, parentUserId }` — a valid
institution-only notice to one known parent — could never be authorized: line 32
does not return (a parent is named), and line 34 always denies because there is no
pupil to derive a guardian relationship from.

`0452cc7` (2026-10-13) landed after the locale acceptance test (2026-10-11), so this
is a cross-ticket regression, not a locale defect. `git diff -- src/lib/auth/communication-policy.ts
src/lib/notifications/service.ts` was empty before this change (HEAD already contained
the regressing guard).

A second latent failure in the same suite, at `tests/locale/database.test.ts:65`:
the report-card dispatch targets `{ schoolId, studentId }` with **no** `parentUserId`
and **no** `recipient`. Under the regressed guard, line 33 threw before the report
path could record its intended `NO_RECIPIENT` status. The test never reached it
because line 46 failed first; the corrected guard must not deny this case either,
because no recipient is ever resolved (nothing is delivered).

## Authorization rule settled on

`assertCommunicationTarget` now applies three distinct, documented rules:

1. **No pupil and no named parent → allow** (unchanged). Institution-only notices
   (e.g. staff deadline reminders) carry no pupil records.
2. **Pupil absent, parent named → school-membership check.** An institution-only
   notice may address one known account directly; the account must be an **active
   `PARENT` of the same school** (`src/lib/auth/communication-policy.ts:45`). This is
   deliberately a school-membership check, *not* a pupil/guardian permission grant.
   It is additionally gated to `permission === "communication"`: a `learningRecords`
   (report card) or `finances` (invoice) dispatch is pupil-record content and is
   refused here, so this path can never be used to deliver pupil data with
   permissions it did not earn.
3. **Pupil present → existing pupil-scoped rules (unchanged, stronger).**
   - With neither a `parentUserId` nor a `recipient`, the dispatch resolves no
     recipient and is recorded as `NO_RECIPIENT` with no delivery; it now only
     requires the pupil to be **live and in scope** (`findInScopeStudent`: matching
     school, optional campus narrowing, `archivedAt = null`, active status,
     unarchived campus). This is the report-card locale-snapshot path.
   - Otherwise the full `authorizedGuardianCommunicationTargets` guardian /
     access-version / channel-consent / exact-recipient check still applies,
     unchanged.

`authorizedGuardianCommunicationTargets` itself was not weakened — the pupil lookup
it already performed was extracted verbatim into `findInScopeStudent` and is reused
by rule 3's no-recipient branch. No permission (`communication`, `learningRecords`,
`attendance`, `finances`), consent, recipient or tenant check was removed.

  `assertCommunicationTarget`, but it hard-refuses to run against anything except its
  own fixture on port `55438` (not the prepared `55401` cluster), so it could not be
  executed here. All of its targets include a `studentId`, so they continue to take the
  unchanged `authorizedGuardianCommunicationTargets` path; the change was verified by
  inspection only, not by running that suite.
- `tests/authorization/access.test.ts` covers the guardian-recipient and foreign-pupil
  denials for this guard but requires a built app and browser; it was not run. Its
  communication cases (`studentId` present) are byte-for-byte unaffected by this change.
- The `permission !== "communication"` gate on the parent-only path is a deliberate
  product judgement (pupil-record content must stay pupil-scoped). If a future
  institution-only notice legitimately needs a different permission, that decision must
  be made explicitly rather than by widening this gate.
