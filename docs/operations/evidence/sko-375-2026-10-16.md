# SKO-375 [005] Approved report versions and publication gates — verification 16 October 2026

Acceptance suite `tests/report-versions/version.test.ts` was **17/20**. The three
failures were all caused by one environment-schema gap: the isolated PostgreSQL
fixture on `127.0.0.1:55438` was provisioned from the Prisma schema (`prisma db
push`) and therefore had **none of the report invalidation/immutability triggers**
declared in `prisma/migrations/20261008021000_report_versions/migration.sql`.
The report-version, correction-resolution and durable-delivery product code paths
in the working tree were already correct; once the migration's triggers were
applied directly (the documented workflow for this ledgerless fixture), the suite
reached **20/20** with no assertion changed.

## Root causes

**All three reduce to the missing `report_source_edit` trigger on `marks`.**

`prisma/migrations/20261008021000_report_versions/migration.sql` defines:

- `report_material_edit` (BEFORE UPDATE on `report_cards`) — a material remark/
  locale/attendance edit withdraws approval and bumps `source_revision`.
- `report_source_edit` + per-source triggers (`marks`, `grade_weight_configs`,
  `subjects`, `students`, `campuses`, `schools`, `classes`) — an upstream source
  edit withdraws approval of every affected report card.
- `report_version_immutable` (BEFORE UPDATE on `report_versions`) — an
  approved/published snapshot cannot be mutated.

The fixture database had **zero** of these triggers (`pg_trigger` returned none
matching `report_%`), because `prisma db push` (the repo's `db:sync` / `db:reset`)
recreates the schema from `schema.prisma` and cannot emit Postgres triggers. The
local instance has no Prisma migration ledger (`_prisma_migrations` is absent), so
migration SQL only exists if it is applied directly — the same situation recorded
for the School AI exam-integrity migration in
`docs/product-review-2026-10/exam-security-implementation.md`.

Chain of causation:

1. `version.test.ts:270` writes `marks.marksObtained = 90` through the raw client.
   With `report_source_edit` absent, `report_cards.remarks_approved` stayed
   `true`, so line 274 failed (`true !== false`). (Had it passed, line 322 would
   next have failed because `report_version_immutable` was also absent.)
2. Because test 1 aborted at line 274, it never approved and published the
   corrected version. `oldVersionId` still equalled the *current* published
   version, so `getPublishedVersion` returned `superseded: false` and test 2
   failed at line 414 (`'false' !== 'true'`). This is a cascade, **not** a family
   resolution defect: `getPublishedVersion` selects `report.publishedVersionId`
   regardless of `requestedVersionId` and only uses the requested id for the
   `superseded` flag, and the PARENT/STUDENT download authorization is
   relationship-driven (`reportScope` → `studentScope(..., "learningRecords")`),
   which is why unlink revocation (test line 420-421) passes.
3. For the same reason only the original version's `REPORT_DELIVERY` event
   existed, so test 3 failed at line 502 (`1 !== 2`). The durable-delivery logic
   itself (re-checking current publication and the frozen `reportVersionId`,
   exactly one provider effect, superseded → `AUTHORIZATION_OR_PUBLICATION_REVOKED`)
   is correct.

Fix: apply the existing, unmodified migration SQL for those triggers directly to
the fixture. No product code, assertion, or mock was changed.

The `prisma:error ... Transaction failed due to a write conflict or a deadlock`
lines printed during the run come from the deliberately concurrent
(`Promise.allSettled`) cases and existing serialization-retry logic; per this
repo's evidence convention they are expected diagnostics on a passing run.

## Remaining uncertainty

- The 55438 fixture has no migration ledger and trigger creation is not part of
  `prisma db push` or `prisma/seed.ts`. Any `db push --force-reset` (or a fresh
  schema-only provision) drops these triggers again and the repair script must be
  re-applied. This is a provisioning gap, not a product-code defect; a real
  release that applies `prisma migrate deploy` gets the triggers from the
  existing migration.
- The pass depends on Postgres-level enforcement for the raw-client assertions
  (`marks` edit withdrawing approval at line 274; snapshot immutability at line
  322). Application-only provisioning cannot satisfy those assertions.
- Verification is backend/HTTP/DB only; no browser screenshots or UI checks were
  performed.
