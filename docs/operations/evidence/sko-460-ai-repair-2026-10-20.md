# AI workflow repair — SKO-460 — 20 October 2026

Ticket: https://linear.app/skoolee-ai-app/issue/SKO-460

The configured OpenAI key is valid. The main assessment failure was inside the application: Zod included JavaScript's 16-digit safe-integer limit in the model output schema, and the privacy scanner correctly treated that number as a possible identifier. Clean paper generation was rejected before reaching OpenAI.

### Implemented
- Removed only redundant machine integer bounds from provider-facing schemas. Original server validation and sensitive-data checks remain intact. Applied the same fix to paper generation, lesson/review generation, written marking, response mapping, parallel forms and the private assistant.
- Aligned capability readiness with the actual approved provider policy; configuration is labeled **Configured**, not a claimed health check.
- Added explicit fictional assistant, curriculum and paper workflows, including editable drafts, marking guides and text downloads. They work locally without AI credits or school-record writes, including when workspace loading or the provider fails.
- Added sample previews for all 19 existing dashboard AI actions.
- Fixed the paper-generation Cancel control, incomplete stream recovery, misleading quota/configuration errors, and stale translation requests. Failed Urdu translation no longer returns English phonetic transliteration as if it were a translation.
- Restored solid header backgrounds, visible active navigation, mobile tool selection, starter prompts, readable reply formatting, and automatic assigned campus/single-subject selection.

### Verification
- **Live provider:** synthetic OpenAI probe; private assistant HTTP 200; lesson draft HTTP 200; Urdu translation HTTP 200; bilingual English/Urdu report remark succeeded.
- **Live assessment:** synthetic curriculum created and approved; paper generation HTTP 200; generated paper saved HTTP 201; same request replay HTTP 200 with identical output.
- **Unit suite:** 391/391 passed.
- **Database suite:** initial 399/402; the three failures were outdated unavailable-provider assumptions and a timer-dependent cancellation fixture. After explicit provider isolation and synchronization on provider startup, all 28 tests in the two affected files passed. Credit, cancellation, receipt and audit assertions remain intact.
- **Browser:** six scenarios passed across the main suite and focused follow-up: sample edit/download with zero AI writes, provider outage preserving input, workspace outage sample access, all 17 workspace tabs, EN/AR/UR mobile layouts, and usable generation cancellation.
- **TypeScript:** all application source plus current isolated Next-generated route types passed.
- Focused ESLint and whitespace checks passed. The global UI-adoption check encountered a concurrent, unrelated onboarding SheetRail native-button change; AI-owned controls use the shared UI components.

### Scope and configuration
All acceptance used the isolated local database and fictional school records. No live school data was used for provider verification. Changes are in the local working tree and are not deployed.

Document-image reading and voice transcription still require their separate configured models and media-processing policy. UTF-8 source upload/manual entry remain available. Marks-photo extraction retains the existing manual review path; this repair does not claim working remote proctoring or secure-browser enforcement.

## Follow-up: complete questionnaire journey — SKO-397 / SKO-460

The earlier verification above covered individual tools. It did **not** cover finishing all guided setup questions. The user's follow-up exposed that gap: completing all 18 questions saved only an ONBOARDING review screen, left 0 saved plans, and made no generation request. This was reproduced through the browser before the follow-up changes.

### Implemented completion flow

- The final answer now leads directly through saving → preparing/saving drafts → completed results. Progress reflects actual requests; reduced motion is respected.
- The complete-school example automatically creates nine saved workflows/policies using the submitted facts. Academic-year/classes and working-day proposals are prefilled for the existing review/apply flow. Fee, assessment and communication policies preserve the supplied terms. Missing roster, curriculum and scheduling dependencies remain visible.
- Configured live AI adds tailored guidance. Missing credentials, provider failure, invalid provider output or a bounded provider timeout produce explicitly labeled prototype drafts from the same saved answers. Prototype preparation consumes no AI credit.
- The package, receipt and successful live credit charge commit atomically. Identical answers replay the same drafts. Refresh during preparation reconnects to the active job; changed answers generate a new package. Concurrent changes or revoked permissions cannot commit stale work.
- Generated results open their exact editors. A prominent academic-review action is immediately available, with compact cards and full-detail disclosures. Editing one reviewed answer offers immediate regeneration without repeating the questionnaire.

### Verified results

- **Complete live-provider browser flow:** all 18 answers entered through the UI → nine saved drafts → refresh/reopen → generic workflow and fee-policy editor handoff → prefilled academic review/approval/preview/apply → one Grade 8 class and one 2026 academic cycle persisted. No year, class or dates were retyped. Changing the fee from PKR 5000 to 6000 generated a new package with the revised terms.
- **Complete no-key browser flow:** the same journey passed with the test server's OpenAI key explicitly empty; result mode was `prototype`, not a claimed live AI response.
- **Interrupted browser flow:** refreshed while the real provider request was pending; the same package appeared, with one POST, one request attempt and no duplicate generation.
- **Phone UI:** actual prototype preparation in EN/AR/UR at 390×844; no horizontal overflow and the primary review action remained in view.
- **Pure suite:** 402/402 passed, including 11 new parser/fact-preservation cases.
- **New database suite:** 6/6 passed, covering live/replay credits, provider fallback, changed/stale answers, cross-campus access, revoked permissions, transaction rollback, concurrent processing and expired-claim recovery.
- Application TypeScript, focused ESLint and whitespace checks passed.

### Deployment limitation

Migration `prisma/migrations/20261020020000_setup_generation_requests/migration.sql` is required before this API can save its receipts. It was applied and tested on the isolated local PostgreSQL database only. An early end-to-end test caught the old database feature constraint; that migration fixes it without changing existing assistant or paper request rules.

The app's configured Supabase connection could not be reached from this environment: migration status failed on the direct connection (port 5432), and a read-only migration metadata query returned `PrismaClientInitializationError: Can't reach database server` on port 6543. No migration or synthetic test data was applied there. The local changes are not deployed; restoring that connection and applying the new migration remain necessary for the configured environment. Tickets remain In Progress for this remaining delivery step.

All browser acceptance used isolated synthetic schools, which were removed after the tests. Only synthetic planning facts were sent to the live provider; real staff/student rosters were not used.
