## Reproduction and boundaries

The bounded harness accepts only the explicitly named `sko386_test` database at loopback port 55439, with matching `DATABASE_URL` and `DIRECT_URL`. It does not load dotenv or reset the shared QA database. `tests/jobs/prepare-current.mjs` deploys the repository migrations to that disposable destination only after `JOBS_ALLOW_RESET=synthetic-only` is supplied.

Run `node --import tsx --test tests/jobs/contract-current.test.ts` for pure tests. With the isolated destination configured, run `node --import tsx --test tests/jobs/current.database.test.ts`; repeat with `TENANT_RLS=true` for the application session path. `tests/jobs/current.api.test.ts` additionally requires the dedicated local app origin and an explicit synthetic auth secret. Each database/API suite deletes only its own synthetic school after removing its dependent activity and guardian rows.

Provider delivery is injected and synthetic; no real email or WhatsApp message is sent. The PDF fixture contains deliberately synthetic approved bytes, so this proves identity, checkpoint and permission behavior, not PDF typography or the academic review pipeline. Receipt tests here exercise stored ingestion; signed-webhook verification is separately covered by SKO-382.

The RLS-session run uses the local database owner. It exercises application session setup and the separate guardian-reader connection, not production grants or non-owner RLS isolation. Production database grants, provider credentials/verified sender configuration, operational callback reachability and real-provider delivery receipts remain deployment checks. They must not be inferred from synthetic fixture success.

The browser seed stores synthetic cookies only in a mode-0600 file under `/private/tmp`. That credential-bearing file must not be copied to ticket attachments or repository evidence. No shared app3107 or PG55438 fixture was changed by this work.
