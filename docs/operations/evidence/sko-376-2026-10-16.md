## Failing tests and root causes

### 1 & 2. `CAMPUS_ADMIN` / `PRINCIPAL`: actual invitation acceptance, landing, no ownership or purchase

Both failed at `tests/memberships/access.test.ts:45`:

```
const actor = await resolveCurrentPrincipal({ userId: account.id, schoolId: school, role });
assert.ok(actor);   // actor === null for CAMPUS_ADMIN and PRINCIPAL
```

**Root cause.** `resolveCurrentPrincipal` enforced a second factor for *every* caller that
passed a `role`, including callers that pass no session claims. Its check was:

```ts
if (claims.role !== undefined && ((requiresMfa(account) && !account.mfaEnabled)
    || (needsMfaChallenge(account) && claims.mfaVerified !== true))) return null;
```

A freshly invited `CAMPUS_ADMIN`/`PRINCIPAL` has `mfaEnabled = false` and cannot have a
verified claim, so the lookup returned `null`. Only these two `INVITABLE_ROLES` are
MFA-required, which is why the same assertion passed for TEACHER/ACCOUNTANT/LIBRARIAN/
RECEPTIONIST/STUDENT/PARENT — the failure was role-specific, not a landing defect.

This became reachable because `928927c` ("enforce … administrator MFA") added the gate and
updated this suite's `cookie()` helper to set `mfaEnabled` and `mfaVerified`, but left the
three direct `resolveCurrentPrincipal(...)` probes (lines 45, 96, 100) untouched. Those
probes are identity/ownership checks — not a browser session.

**Fix.** `src/lib/auth/principal.ts` now applies the MFA gate only to full session claims,
which always carry `accessVersion`. Identity/ownership probes pass a role with no version
and are no longer turned into an MFA gate:

```ts
if (claims.role !== undefined && claims.accessVersion !== undefined
    && needsMfaChallenge(account) && claims.mfaVerified !== true) return null;
```

Every real session (`issueSession`, `mfa-ticket`, `first-password`, `completeOnboarding`,
`completeTeacherOnboarding`) sets `accessVersion`, so `getAuthUser`, the tenant guard and
`proxy` enforce MFA exactly as before. The unused `requiresMfa` import was removed.

### 4. one-campus group admin has no ownership; explicit standalone owner retains setup

Failed at `tests/memberships/access.test.ts:96`:

```
const admin = await resolveCurrentPrincipal({ userId: accepted.get('CAMPUS_ADMIN')!, schoolId: school, role: 'CAMPUS_ADMIN' });
assert.equal(admin?.isInstitutionOwner, false);   // undefined, because admin === null
```

**Root cause.** Identical to 1 & 2 (the `CAMPUS_ADMIN` principal was `null`). The
standalone-owner half of the same test resolves an `ADMIN` owner, also MFA-required, and
had the same gate applied. The lesson: the one-campus `GROUP` admin is correctly
non-owning; the ownership lookup was simply denied before it could be asserted.

**Fix.** The same `principal.ts` change. No ownership logic changed: `isInstitutionOwner`
is still read from the account, and `assertInitialInstitutionSetup` still requires an owner
whose role is `SUPER_ADMIN`/`ADMIN` and whose email matches the institution registration
contact.

### 3. owner invitation creation uses explicit delegation; student administrative delegation is rejected

Failed at `tests/memberships/access.test.ts:77`:

```
const response = await request(owner, '/api/staff', { email, role: 'ACCOUNTANT', campusId, canPurchaseSubscription: true });
assert.equal(response.status, 201, await response.text());   // 503
```

Observed body: `{"error":"Invitation saved, but email could not be delivered. Use Resend Invite to try again."}`

**Root cause.** The invitation was created and its delegations (`canPurchaseSubscription:
true`, `canManageMemberships: false`) persisted, but `inviteStaff` treated *any* failed
delivery attempt as a failed request. The isolated environment runs with
`DISABLE_OUTBOUND_MESSAGES=true`, so `deliverEmail` returns "Outbound email is disabled"
and `sendInviteEmail` throws "Email dispatch failed"; the catch then threw `503`, hiding a
created invitation and its link. The explicit-delegation checks themselves
(`createStaffInvitation`) were correct — the API simply never returned its success body,
and the second assertion (STUDENT + administrative delegation → 400) never ran.

**Fix.** `src/app/actions/invite.ts` now fails loudly only for a genuine delivery problem.
When the provider is deliberately suppressed (`emailProviderReadiness().mode` is
`"disabled"` or `"development"`), the invitation remains saved, `deliveryStatus` is recorded
as `failed`, and the request proceeds to return `201` with the invitation link. An
unconfigured or failing real provider still returns `503`, so
`tests/account-lifecycle/delivery.test.ts` (unconfigured provider → `503` + `deliveryStatus
'failed'`) and `tests/recovery/provider-readiness.test.ts` (`sendInviteEmail` still rejects
in a development bypass) keep their contract. `deliveryStatus` is never set to `sent` when
nothing was delivered.

## Remaining uncertainty

- The `principal.ts` change preserves MFA enforcement for every token that carries
  `accessVersion`, which all session-minting paths do. A hand-crafted token that omits
  `accessVersion` and `mfaVerified` is treated as an identity probe; such tokens are not
  minted by the application, but the change means the guard is no longer a defence against
  that specific forged shape. The login route remains the enrollment gate, and
  `getAuthUser`/the tenant guard still reject any unverified session claim that carries a
  version.
- `resendInvitation` still returns `503` when delivery is suppressed (it was not needed by
  the acceptance suite). If product wants resend to behave like create in a suppressed
  environment, that is a follow-up decision.
