# SKO-213 — Auditable grade and finance corrections

Implemented at `/corrections`, linked from the shared role sidebar. English, Arabic and Urdu controls, responsive before/after values, original currency formatting, keyboard confirmation, screen-reader status, date/type filters, session-scoped expiring drafts, private notes, redacted JSON history/receipts and authorized original-document links are included.

## Integrity and authorization

- Correction requests and original/proposed evidence are append-only; the only permitted transition is a single approved/applied or rejected decision. Private notes live in a separate tenant/campus-scoped table. Actors, names, timestamps, source revision and successor references are retained.
- Preview hashes bind the exact source revision, grade rules, invoice balances, original ledger/account identity, allocations, credit and school approval policy. Serializable apply transactions reject concurrent/stale changes and preserve pending requests.
- The school policy defaults to a separate approver. It is enforced for correction approval and renewed report approval, including after a later edit supersedes the initial pending report version. Direct API self-approval is rejected.
- Grade changes use SKO-210 `refreshVersion` and exact-version approval/publication. Existing published report bytes remain unchanged. Families see the correction only after all affected reports have an approved publication containing that correction or a later successor.
- Payment corrections append a negative payment, negative allocations and a compensating ledger entry. The source receipt, currency and account identity remain unchanged; all affected invoice balances and available carry-forward credit reconcile in original minor units. PKR, SAR, AED, KWD and USD are covered; there is no FX conversion.
- Both legacy payment-entry endpoints now use the shared collection helper. Collections serialize invoice allocation and only add the newly created overpayment credit, avoiding cumulative credit duplication.
- New receipts capture a snapshot at collection and cache immutable PDF bytes. Legacy receipts without a snapshot are captured before their first correction/download; pre-existing external receipt references remain intact. This cannot retrospectively reconstruct an old document that was never retained by the prior implementation.

## Boundaries

- This adds mark corrections and compensating payment reversals, not country-specific refund/credit-note rules (SKO-256).
- Legacy records with missing ledger entries, inconsistent allocations/currency, cancelled invoices or consumed credit fail closed and require reconciliation; no accounting values are guessed at commitment.
- Original allocation migration derives the existing single-invoice model chronologically. The new allocation ledger and integration tests support multiple affected invoices; this issue does not add a separate payment-allocation editor.
- No production database, provider credentials, outbound notifications, merge or deployment were used in validation. Local synthetic evidence is not production certification.
