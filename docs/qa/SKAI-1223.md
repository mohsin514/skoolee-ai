# SKAI-1223: first-school onboarding from an empty tenant (QA runbook)

Archived as SKO-281. Live QA was blocked because the check "needs creating an empty tenant". This runbook
removes that blocker: an empty tenant is created through the product's own self-serve registration, so no
seed change, database edit or platform-owner action is needed. It does not record a QA result. QA attaches
evidence to the Jira card and moves it to Done.

## Why the seeded tenants are not used

None of the `qa:seed` tenants (`docs/qa/TEST-ACCOUNTS.md`) starts at "empty". `T6 Zeta Empty` is already
onboarded with zero records, so it suits empty-state checks but skips the setup wizard. This check starts
with a brand-new owner and no institution.

## Setup

1. Use a local app or an isolated QA lane (`docs/qa/QA-ENVIRONMENT.md`, `scripts/qa/app.sh`), never production.
   Outbound messages stay disabled, so the email OTP is read from the app log or the lane's mail stub.
2. Pick a synthetic address on the reserved TLD, for example `skai1223-<date>-owner@example.invalid`, and the
   shared QA password from `docs/qa/TEST-ACCOUNTS.md`. Never use a real school or a real person's data.
3. No feature flag is needed. AI setup without a provider key shows labelled starter drafts; that is not
   evidence of live generation.

## Steps

Run once as a **single school** owner and once as a **school group** owner (the `registrationType` options in
`src/lib/auth/register.ts`).

| # | Action | Expected |
| --- | --- | --- |
| 1 | Open `/register`, choose the registration type, fill the synthetic details, submit | Account created; role is `ADMIN` (single school) or `SUPER_ADMIN` (group); no school records yet |
| 2 | Verify the email code, sign in | Lands on `/onboarding` ("Let's set up your institution"), not a dashboard or spinner |
| 3 | Complete structure and identity, then refresh the page mid-step | Saved answers are kept; no redirect loop |
| 4 | Package step | Plan is visible; free/test checkout continues without a real payment |
| 5 | Campuses step: one primary campus (single) or two or more campuses (group) | Campus drafts survive sign-out and sign-in |
| 6 | Academic step and review, then activate | The campus becomes active and the owner continues to `/ai?setup=1` |
| 7 | Open the role dashboard | Empty states with a next step on every list (students, classes, fees); no other school's data |
| 8 | Repeat steps 2 and 6 with `?lang=ar` and `?lang=ur` at 390 px | Right-to-left layout, nothing clipped |
| 9 | Denied role: sign in as `t6-super_admin@example.invalid` and as a seeded teacher, open `/onboarding` | Not offered institution creation for the new school; teachers see the no-access explanation |

Name screenshots `SKAI-1223_<nn>_<step>_<EN|AR|UR>.png`. Remove the throwaway school afterwards from the platform
owner school list, or reset the lane.

## Existing automated coverage

These suites already drive the same path against the isolated database (they create and delete their own
owners and schools):

- `npm run test:onboarding:browser` (`tests/onboarding/onboarding.browser.test.ts`): standalone owner with one
  primary campus, group owner with three campus drafts that survive failed checkout and sign-out, failed
  completion recovery, handover, non-owner staff no-access, AR/UR right-to-left at 390 and 1440, deferred MFA.
- `tests/onboarding/session-before-campus.browser.test.ts`: a session before any campus exists.
- `npm run test:onboarding` and `npm run test:onboarding:db`: setup state and database rules.
- `tests/design-system/auth-register/register.spec.ts`: the registration screens.

The live QA run above is still required; the automated suites are supporting evidence, not a substitute.
