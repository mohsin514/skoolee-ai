# SKO-223 — Job status, retries and delivery receipts

New report delivery, approved-PDF preparation and bank-statement import requests return a persisted activity job identifier. Their existing start screens open `/jobs?id=…`; `/jobs` lists authorized activity. English, Arabic and Urdu interfaces retain current totals during refresh, expose selection-based failed-item recovery, distinguish processing from provider receipt evidence, and export the persisted receipt as JSON.

## Contract

- A delivery item refers to the existing communication and its immutable `reportVersionId`. The item links to the existing F70 workflow; successful recipients are never re-enqueued. Missing guardian contacts are corrected in the pupil workflow and resolved again on retry. A newer publication rejects recovery of the superseded version rather than replacing its content.
- A PDF item reads the exact approved artifact bytes and records its version-specific download reference. Approval already generated the artifact; this job prepares/checks that artifact, not a new mutable rendering. An expired lease resumes via the durable effect checkpoint.
- A bank import persists the bounded CSV and original currency before work starts. One file is one item. Matching and creation of its reconciliation record share the durable effect transaction. Repeating the same input resolves the same job. Invalid files remain failed; corrected files start a distinct import. Student CSV imports are outside this implementation.
- Queued/running/completed/failed/cancelled counts partition the persisted item set. Provider acceptance is shown only with a recorded provider message identifier; delivery and read require signed WhatsApp receipt evidence. SMTP delivery/read evidence remains unavailable. Provider-reported delivery failure is retained separately from completed processing.
- Retry and cancellation require current school/campus/class scope and module edit permission. Read-only staff retain results without mutation controls. Cancellation records an audit entry and preserves successful and in-flight accepted deliveries. Unknown external outcomes remain blocked pending provider reconciliation; a transport failure is not permission to resend.
- Meta POST ingress now requires `WHATSAPP_APP_SECRET` and the matching `WHATSAPP_PHONE_NUMBER_ID`; it verifies the raw-body HMAC before parsing and deduplicates receipts. Persistence failure returns 500 so the provider can retry. No live provider certification is claimed.

## Validation

Only disposable PostgreSQL `127.0.0.1:55423/sko223` and app port 3223 were used. Tests refuse other database URLs, create synthetic tenants, and disable real outbound delivery. No remote environment file, remote fixture, production migration or deployment was used.

- Three integration scenarios: 100 recipients with 97 provider acceptances and missing-contact/expired-authorization/provider-unavailable failures; failed-only retries; duplicate and late callbacks; a child PDF worker killed after a committed checkpoint; one committed bank reconciliation after replay; invalid-file categorization; in-flight cancellation; uncertain-outcome retry refusal; and superseded-version retry refusal.
- Nine actual HTTP cases cover report/PDF/import starts and durable identifiers, cross-tenant and cross-campus read/retry denial, read-only cancellation denial and unsigned callback rejection.
- Browser evidence covers 119 API/UI combinations: all 11 roles, desktop/tablet/phone and English/Arabic/Urdu, plus keyboard selection, same-job reload, read-only controls and overflow checks. Screenshots and machine-readable results are in `docs/qa/evidence/sko-223`.
- TypeScript, targeted ESLint and a production Next.js build were checked locally. The scoped GitHub workflow repeats migration, typecheck, domain scenarios, production build and HTTP verification.

## Operational boundaries

The durable outbox worker must run for queued PDF/import/delivery work. The migration adds activity and receipt tables; it has only been applied locally. Optional RLS policies are supplied alongside the repository's existing opt-in policy script; enabling RLS and the separately privileged provider/dispatcher service remains an operator rollout. Existing historical jobs are not backfilled. Outbox uncertain-effect reconciliation remains the existing operator responsibility and is intentionally not bypassed by this UI.
