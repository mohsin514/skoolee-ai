## 1 Decision summary

The three judges split their winners: security picked A2, the tech lead picked A1, the founder picked A3. On aggregate score A3 is ahead (116 against A2 112 and A1 110), so this architecture keeps **A3's spine**, with three parts:

1. **One uniform registry entry per Appendix A capability**, keyed by the inventory key.
2. **Plan-then-execute**, where the model never emits ids. It emits typed `EntityRef`s, and scope-filtered server resolvers bind them.
3. **Breadth economics.** The roughly 106 class-C inline-prisma rows are covered by a hand-off plus a two-line `completeHandoff()` hook, not by extraction.

Two other designs are grafted onto that spine:

- **From A1, the type system and the build lint:**
  - class C is a separate TypeScript type with no `execute`;
  - an AST route scanner with a ratchet runs inside `npm run build`;
  - gate provenance must match the route's guards;
  - a write-ahead intent ledger;
  - an explicit person-key allow-list fix in `pseudonymize.ts`;
  - services export their zod input schemas.
- **From A2, the runtime:**
  - normalised job, step, question, confirmation, hand-off and event tables (prefix `AiWorkflow*`, because `WorkflowJob` already exists at `schema.prisma:373`);
  - full job and step state machines with a rendering for every state;
  - a two-phase strict-JSON model protocol with a single-step fast path;
  - questions bound to a step and a JSON-pointer field, using localized templates;
  - `fingerprint()` drift detection leading to STALE;
  - an UNCERTAIN state that is never auto-retried;
  - a lease plus heartbeat, and SSE over a seq event log with polling fallback;
  - questionnaire version binding with a plan diff;
  - five hand-off kinds;
  - compensation offered as a newly proposed step.

The questionnaire is a **deterministic compiler** from typed per-role answers into the same plan and executor, ending in readiness computed from live records.

All judges' mustFix items are resolved in §6, §7 and §8:

- APPROVAL_DECISION is class C.
- Class-B typed-op approvals are hash-bound, or escalate.
- Hand-offs are single-use and actor-bound.
- Route-only side effects move into commands.
- School content travels in a delimited data channel, with red-team tests.
- Every provider attempt has its tokens logged.
- Class counts are regenerated by a committed script.

**Trade-off accepted.** There are more tables than A1 proposed, and we do not extend `SchoolAiRun` for chat jobs. In exchange, SKO-470's scheduled-run code stays untouched and APP_OWNER/SUPER_ADMIN jobs without a campus are possible. SKO-470 reuse happens at the execution layer (records, preview, `executeSchoolAiToolInTransaction`, `SchoolAiExecution`, Runs), which is where its guarantees live. Founder override D1 can switch to extending `SchoolAiRun`.

## 2 Glossary (plain words)

| Term | Meaning |
|---|---|
| Capability | One thing a user can change in Skoolee, for example "lend a library copy". Appendix A lists them; key = inventory key. |
| Registry entry | One TypeScript object describing a capability: who may use it, its input, its preview, how it runs or hands off, and its receipt. |
| Adapter | The `execute` (or `handoff`) part of an entry. It calls an existing service function and never a route handler or SQL. |
| Job | One request ("issue Atlas to Ayesha") or one questionnaire submission, with its plan. |
| Plan / Step | A job's ordered list (a DAG) of steps. Each step is one capability with bound inputs. |
| EntityRef | What the model writes instead of an id: `{ $ref: "student", text: "[STUDENT_1]", hint: "7B" }`. |
| Resolver | Server code that turns an EntityRef into a real id, but only among records the user may see. |
| Class A | Runs as soon as it is ready (reads, own profile, private plans). |
| Class B | Runs only after the user presses Confirm on the exact preview shown (hash-bound). |
| Class C | The engine never applies it. It prepares a hand-off to the existing approval or domain screen, and a human with authority presses that screen's own button. |
| Hand-off | The prepared class-C item: a record awaiting approval, a domain request, a prefilled screen, a task for another role, or a deep link. |
| Preview hash | Fingerprint of exactly what the user saw. A confirmation is only valid for that hash. |
| Receipt | Proof of what changed: model ids that are read back from the database, plus counts and a deep link. |
| Outcome | The honest summary of a job: EXECUTED, AWAITING_APPROVAL, PARTIAL, ANSWERED, PLAN_SAVED, NOTHING_DONE. |
| Readiness | Per-role checklist computed from live records. It never comes from "questionnaire finished". |
| Exclusion | An Appendix A row deliberately not automated, with a reason (auth flows, webhooks, crons, MFA billing, legacy duplicates, Exam Studio-owned rows become deep links). |

`defineVariants()` splits multi-action operations into separately classed entries. Example: `setup.apply_changes` (`school-setup-service.ts:124-151`) becomes:

### 3.3 Never-safe list (lint and review, from A3)

- **Never invoke route handlers.** `requireAuthUser()` reads `cookies()`, so it would get the wrong principal or none in the worker.
- **Never forge `Origin`** to get past `assertSameOrigin`.
- **No adapter depends on headers, IP or capacity wrappers:** `measured()` / `requestSchool()`, IP-keyed limits, or the support-grant cookie.
- **No FormData uploads.** Those are deferred to SKO-460.
- **A synthesized `NextRequest` is allowed only** for callees listed in `registry/wrappers.ts` (today `createStudentRecords`, `students.ts:21-22`), and only transitionally.
- **No model-chosen HTTP or SQL** anywhere.

## 5 Model protocol

### 5.1 Tool retrieval: code first

1. **Role filter.** `registry.forRole(user)` checks the static gate parts: role, module flags from the permission snapshot, capability keys, seats. This leaves TEACHER with about 150, PARENT about 48, operators about 520.
2. **Lexical rank.** BM25 over EN/AR/UR titles, keywords and examples (`search-index.json`), against the normalised, **masked** request.
3. **Router call** (from A3), only when more than 40 candidates remain after rank cut. Input: domain cards. Output: `{domains[≤3], intent}`. 300 tokens, 8 s, strict JSON.
4. **Live gate check** on the ≤20 candidates. Failing-but-role-listed capabilities become a "not available because… whoCan" list, so the model can answer honestly. Gaps go to `AiCapabilityGap`.
5. **Escape hatch.** `needCapabilities` may be used once per job and triggers a second retrieval.

Embeddings stay off (D7).

### 5.2 Cards (what the model sees)

A card holds id, title, `whenToUse`, two examples in the request language, inputs with `.describe()` text, a class note ("You must ask the user to confirm" / "This prepares it for {roles}; it does not apply it"), and `produces`.

Ids never appear: id fields are `EntityRef` objects. The model is told the class so it can phrase expectations, but **no protocol field it writes is read as a class**.

### 5.3 Two-phase, strict JSON

All calls go through an extended `generateAIDraft`, with `responseFormat: { name, schema, strict: true }`, so that OpenAI receives `response_format: json_schema` (B.engine: no JSON mode today, `openai-settings.ts:12-17`). OpenAI stays the provider.

At job start, a readiness probe refuses jobs if the configured `OPENAI_MODEL` rejects strict `json_schema`, with a localized error.

**Phase 1, plan** (temperature 0, ≤1,500 output tokens, 20 s):

```ts
planProposal = z.strictObject({
  kind: z.enum(["plan","answer","ask","unsupported"]),
  steps: z.array(z.strictObject({ key: z.string().regex(/^s\d{1,2}$/), capability: z.string(),
    dependsOn: z.array(z.string()).max(6), forEach: z.strictObject({ ref: z.string() }).nullable(),
    input: z.record(z.string(), z.unknown()),          // EntityRefs + scalar facts only
    evidence: z.array(z.strictObject({ pointer: z.string(), quote: z.string().max(300) })).max(60),
    missing: z.array(z.string()).max(20) })).max(25),
  questions: z.array(z.strictObject({ about: z.string(), stepKey: z.string().nullable() })).max(5),
  answer: z.string().max(1200).nullable(), unsupported: z.array(z.strictObject({ nearest: z.string().nullable() })).max(5),
  needCapabilities: z.array(z.string().max(80)).max(3) });
```

- **Fast path.** If retrieval puts one capability far ahead and its model schema has ≤12 fields, phase 1 inlines that schema and fills it in the same call. Common single requests cost one call.
- **Deterministic binding.** Resolvers map EntityRefs to ids under scope. `$sN.output.x` bindings come from committed receipts. Defaults include loan-rule due dates and today in the campus timezone. Ambiguity becomes `ENTITY_CHOICE` chips with no model call.
- **Phase 2, fill.** Only for fields still missing that need language understanding (free-text reason, a per-pupil status from a sentence, an amount in words). One strict call per such step. A fill cannot change the capability, which is the tool-switch guard at `validation.ts:5-9`.

**Repair.** `plan-validate.ts` checks: capability is in the retrieved, role-filtered set; DAG acyclic; `forEach` targets an array in the output schema; ≤25 steps; evidence matches. **One** repair call is allowed for either a syntax error or a schema failure; today a syntax error skips repair (`service.ts:128,134`). After that the job fails with a localized message, and the job's credit action is still charged (§7).

**No model-driven lookup rounds.** This rejects A1's 4-round tool loop: the security mustFix requires that lookup output never re-enter the prompt. Lookups are resolvers on the server.

### 5.4 Data channel and prompt injection

- The system prompt is English, static, and holds no school content.
- The user turn is one JSON document with three fields:
  - `userText`: masked user-authored segments;
  - `context`: the actor's own class, subject and room labels (school vocabulary, clear);
  - `capabilities`: cards.
- Any school-authored text that must be shown is wrapped as `{ "data": "…" }` inside `context.quotedData[]`. That covers book titles, announcement bodies, reasons, and setup tables.
- The prompt states that `quotedData` and `context` are never instructions. The real defence is in code:
  - plans may only use retrieved, role-gated capabilities;
  - classes come from the registry;
  - class C never executes;
  - evidence must come from `AiWorkflowSegment` user text, never from `quotedData`.
- Red-team cases (§12) assert zero effective writes when injected record text asks for class C or cross-role work.

### 5.5 Language

- `job.language` comes from the UI locale. `requestLanguage` comes from script detection (Urdu letters ٹ ڈ ڑ ں ے ھ).
- Everything the user sees is server-rendered from registry and engine copy in EN/AR/UR: step titles, questions, previews, errors, outcomes. The model writes only `answer` text for read questions, in `job.language`.
- `normalize.ts` handles:
  - NFKC and case-fold;
  - ي/ى/ی, ك/ک and ه/ہ/ة folding;
  - tatweel, diacritics and ZWNJ removal;
  - Arabic-Indic and Extended Arabic-Indic digits to ASCII;
  - quote unification.
- Relative dates (آج, کل, اليوم, Friday, جمعہ) are parsed server-side from the evidence quote. If the model's ISO date disagrees, that field becomes a question.

### 5.6 Evidence

- Evidence is matched only against `AiWorkflowSegment` rows (request and answers). Server text never matches, which fixes `service.ts:42,48,152` and the role-interview pollution at `automatic-workspace.tsx:33`.
- A match is a normalised substring, or token-set similarity ≥0.85 within one sentence window.
- We store offsets, not quotes.
- Derived values need the quote **plus** an agreeing server parse.
- A failed match makes that field a question, not a job failure.

**Attendance** (judge mustFix): the input carries an explicit `rule: { default: "PRESENT", quote } | null`. "Rest present" applies only when the user said so ("all present except Ali and Sara"). A bare "mark all present" becomes a deterministic count question ("Is everyone in 7B (32 pupils) present today?"), still class B with the full roster in the preview. Per-pupil evidence never comes from server-rendered roster text.

### 5.7 Pseudonymisation fix for class and subject names

1. **Shared classifier fix (from A1)** in `pseudonymize.ts:36-37`. Replace the two patterns with an explicit person-key allow-list: `fullName, studentName, guardianName, parentName, fatherName, motherName, teacherName, staffName, contactName, principalName, displayName`. `name` counts as PERSON only when the object has `kind: "person" | "student"`.
   - Regression tests: `className`, `subjectName`, `campusName`, `schoolName` and `roomName` stay clear.

2. **Policy masking by entity kind (from A2/A3)** in `pii/masker.ts`. CLASS, SECTION, SUBJECT, ROOM, PERIOD, FEE_HEAD, BOOK_TITLE and CYCLE labels go through verbatim. STUDENT, STAFF, GUARDIAN and MEMBER become tokens. Phones, emails, ids and addresses are removed.

**DOMAIN_SCREEN safety** (mustFix: payment unique is `(schoolId, recordedBy, idempotencyKey)`):

## 7 Idempotency, receipts, audit, credits

### 7.1 Idempotency layers

These keep every strength B.engine found.

1. **Job start:** `(schoolId, actorId, idempotencyKey)` + `requestHash`. A different hash gives 409. A P2002 race reloads, as `run-service.ts:70-78` does.
2. **Command:** `clientCommandId` unique per actor.
3. **Step key:** `wf-{jobId8}-{stepKey}-{attempt}`, matching the `execution.ts` regex. `attempt` changes only when the preview changes. The key is persisted before execution.
4. **Intent ledger** (`AiWorkflowIntent`), written **before** the service call:
   - If an existing row is COMMITTED, replay its receipt.
   - If it is INTENT (the crash window), run `reconcile()`. Found means RECONCILED. Not found means **UNCERTAIN**, with retry disabled until a human checks ("Check this in Lending desk"). It is never blindly re-executed.
   - The same key with a different `inputHash` gives 409 `STEP_INPUT_CHANGED`.
5. **Adapter mode:**
   - `native`: fees collect, `logCall`, `importBatch`, `executeSchoolAiTool`.
   - `tx-receipt`: the target for every extracted command. The service takes `{ tx }`, and intent COMMITTED is in the same serialisable transaction (`transaction.ts:13-39`).
   - `natural`: issueCopy (`desk.ts:95`, opens its own transaction, 409 at :112-113), requestLeave (`leave.ts:44-45`). These have DB kill tests (§12).
   - `convergent`: registers, with `knownStatus` concurrency.
6. **Lint:** an inventory row marked `idem = no` must declare `natural` + `reconcile` or `native`, or go to `exclusions.ts`. Examples of deferrals: `fees.record_payment_basic` (use `fees.collect_payment`), `staff_attendance.mark_staff`.
7. **Library renew** reconciles on the renewal count, because a replay would renew twice.

The school-wide `FOR UPDATE` lock on role actions (`role-action-service.ts:22-24`) is replaced by per-key uniqueness plus the domain's own locks.

### 7.2 Receipts and honest outcomes

- `receipt()` picks ids by declared paths. Wrapper responses require `ok` + `success: true` + an id path, and a 2xx alone is never enough.
- A 409 with `conflicts[]` (attendance route `:56`) maps to step `CONFLICT`, which becomes a question.
- `verify()` reads every id back under `runWithTenantContext`. A failure means `FAILED_UNVERIFIED`, an alert, and the outcome can never be EXECUTED.
- Outcomes (`outcome.ts`, generalising `validation.ts:12-17`):
  - EXECUTED: ≥1 verified write, no open hand-offs, nothing blocked;
  - AWAITING_APPROVAL: open hand-offs;
  - PARTIAL;
  - ANSWERED: reads only;
  - PLAN_SAVED: drafts only;
  - NOTHING_DONE.
- `queued` effects read "queued, not delivered".
- Leave requests read "Sent; the school decides".

### 7.3 Audit

Every execute, confirm, hand-off create, claim and complete writes:

```
auditLog { tableName: "ai_workflow_steps", recordId: stepId,
           newValue: { capability, version, class, idempotencyKey, receiptRefs, confirmedById, previewHash, claimantId, completedById } }
```

This is in addition to the domain's own audit. `AiWorkflowEvent` payloads carry ids and template keys only, and a test scans them with `scanForPII`.

### 7.4 Credits (decided)

- **One AI action** = one phase-1 plan turn (including its router call and ≤1 repair), or one phase-2 fill, or one free-text questionnaire parse batch. It is charged **one credit whether or not it succeeds**.
- Tokens for **every** provider attempt are logged against the job through `consumeAICreditAndLog` (`openai.ts:522`). This is the security mustFix: no free malformed spend. Repairs and router calls never add a second credit.
- Executing adapters, replays, chip answers and deterministic compilation cost 0.
- **Reservation.** At plan time, `reserveAICredits(schoolId, estimate)` (`openai.ts:505-511`) runs in the job-create transaction. The estimate is 1 + expected fills + 1 replan buffer; for a questionnaire it is the free-text cells / 2. The estimate is shown in the UI before start.
- `lockAndReconcileAICredits` (`:490-503`) releases expired workflow reservations under the same school lock.
- **Exhaustion** sets `PAUSED_CREDITS` (not FAILED), with neutral copy and resume. Committed steps stay.
- Plan limits in `src/config/plans.ts` are untouched.
- Founder override D4: do not charge failed actions.


## 11 Observability and ops

**Job states** (A2), each rendered in `step-card` / `workflows-home`: PLANNING, NEEDS_INPUT, REVIEW, RUNNING, WAITING_CONFIRM, WAITING_HANDOFF ("you can close this"), PAUSED, PAUSED_CREDITS, BLOCKED_ACCESS, REPLANNING, COMPLETED (+ outcome), FAILED, CANCELLED, EXPIRED. Expiry is 24 h for free-form and 14 days for a questionnaire.

**Step states:**
- PROPOSED, NEEDS_INPUT, FILLING, READY, WAITING_CONFIRM, QUEUED, RUNNING;
- SUCCEEDED (+ Undo… when compensation exists);
- CONFLICT, HANDED_OFF, COMPLETED_ELSEWHERE, COMPLETED_WITH_CHANGES;
- DENIED ("only the principal does this here" + ROLE_TASK offer), UNSUPPORTED, STALE, BLOCKED;
- UNCERTAIN (retry disabled), FAILED_UNVERIFIED;
- SKIPPED, DECLINED, SUPERSEDED, FAILED, CANCELLED.

Transitions are the pure `nextStepState()`.

**Throughput and timeouts:**
- A command locks the job row (`SELECT … FOR UPDATE`, as in `run-service.ts:91`) and claims a 45 s lease (`leaseOwner=REQUEST`). It runs **one bounded unit**: one model call (≤20 s), or ≤5 class-A executions, or one B or C transition. Then it returns the snapshot and `eventSeq`. That keeps every route well under `maxDuration = 60` (`automation/[id]/route.ts:5`).
- The rest gets `nextWakeAt = now` for the worker. The worker claims via `updateMany where version + lease expired`, heartbeats every 15 s, and checks `leaseToken` on every persist. It runs a fair round-robin by school (limit 24, 2 per school, D10).

**Progress:**
- SSE at `GET /events?after=seq` (pattern of `api/notifications/sse/route.ts:91`), with a 1 s DB poll inside the stream, or Redis pub/sub when `REDIS_URL` is set. The stream closes before `maxDuration`, and the client reconnects with the last seq.
- Fallback: `?after=seq&poll=1` every 2 s.
- Commands are queued offline with `clientCommandId`. Confirmations are not.
- Closing the tab is safe: A work continues, B and C wait.

**Retention (D9):** events 90 days; jobs, steps, questions and segments 1 year; intents and receipts as long as the domain record; legacy AUTOMATIC_* rows archived after 30 days. Run via `src/app/api/cron/ai-workflows-retention/route.ts`.

**Cancel:** any non-terminal job. Steps not yet run become CANCELLED and committed receipts stay listed. Open hand-offs become SUPERSEDED and their screens show "withdrawn".

**Metrics** (structured logs, ids only): plan latency p50/p95, model calls per job, questions per job, wrong-class attempts (must be 0 effective), UNCERTAIN count, hand-off age, reservation leakage, sweep lag.

**Before W1, measure:** token size of 20 cards + strict schemas, p95 for phase 1, and the fast-path hit rate. If the budget fails, shrink cards to 12 and keep schemas only for the fast path.

- There are five hand-off kinds: RECORD_APPROVAL, DOMAIN_REQUEST, DOMAIN_SCREEN, ROLE_TASK and DEEP_LINK. A DOMAIN_SCREEN hand-off is single-use and bound to one actor. It is re-authorised for the viewer, claimed through a CAS from OPEN to CLAIMED, and its prefill hash is checked at submit. Completion runs in the same transaction as the domain write, with the claimant as recordedBy. It ends as COMPLETED or COMPLETED_WITH_CHANGES, the latter with a diff.
- Idempotency is layered: job key and hash, then clientCommandId, then a wf- step key, then the intent ledger, then the adapter mode (native, tx-receipt, natural or convergent). An inconclusive natural reconcile leaves the step UNCERTAIN with retry disabled. verify() reads every receipt id back under the tenant guard, and a failure gives FAILED_UNVERIFIED. - Pseudonymisation. The shared classifier at pseudonymize.ts:36-37 is fixed with an explicit allow-list of person keys. - Credits. One AI action is a plan turn, a fill, or a free-text parse batch, and it costs one credit even when it fails. Tokens for every attempt are logged. Repair and router calls are never charged separately. Credits are reserved at plan time and the estimate is shown before the run. Running out pauses the job (PAUSED_CREDITS). Execution and deterministic compilation are free.

**Risks**
- Planner precision across about 150 (TEACHER) to about 520 (operator) capabilities has not been measured. Retrieval recall and the fast-path hit rate need the live-smoke suite before W1, and the token budget for 20 cards with strict schemas must be measured first.
- Free-text person names that match no school entity, especially Arabic or Urdu names against Latin-stored rosters, can still reach the provider. The [PERSON_n] heuristic and scanForPII reduce this but do not eliminate it (D9).
- About 117 inline-prisma B/A extractions and schema exports on about 265 direct rows dominate the cost. The work also touches shared files in a shared checkout (schema.prisma, tenant-models.ts, copy catalogs).
- Fixing the shared pseudonymize.ts classifier changes masking for existing callers such as Exam Studio. Their suites must re-run in the same PR.
- Natural-key reconcile (issueCopy, requestLeave, renew, enquiries) can leave steps UNCERTAIN until those services gain a tx variant. A wrong reconcile query could falsely report a replay; the DB kill tests mitigate this.
- Class-C DOMAIN_SCREEN coverage depends on about 50 screens adopting useWorkflowHandoff and completeHandoff. Until then the hand-off falls back to a deep link with a values panel, which is honest but weaker in a demo.
- Removing self-approval changes how existing typed ops behave. Admins will see confirmations or hand-offs where they used to get auto-execution, so setup flows need end-to-end retesting.
- Questionnaire steps that cross into another role's seat depend on other people acting. Readiness will often stay PARTIAL or WAITING_HANDOFF for days, which is a demo risk even though it is honest.
- SSE is time-boxed on serverless hosts and worker capacity is unmeasured, so progress may feel slow under load.
- Appendix A comes from static reading with verifier corrections and duplicate tables. Every adapter must re-audit its row at file:line, and the counts are provisional until coverage.md is generated.
- The release gate (CURRENT_AI_RELEASE_EVALUATION = null) blocks real tenants until an educator-reviewed evaluation that includes automation cases is recorded. LEAP must run on a synthetic tenant.
- The permissions V2 cut-over on 2026-10-26 and per-school overrides can shift effective gates, so the matrix must run both before and after.
- Boundaries with SKO-470 (records and Runs), SKO-460 (conversation and composer) and Exam Studio (the deep-link-only rule) need owner sign-off.
