### Job state machine
`RUNNING | WAITING_INPUT | PAUSED | COMPLETED | FAILED | BLOCKED` (`schema.ts:32`). Client actions: `advance | answer | pause | resume` (`schema.ts:8`). Transitions in `service.ts:98-157`:
- `pause` RUNNING→PAUSED (98); `resume` PAUSED/FAILED→RUNNING and clears `error` (99).
- `answer` only from WAITING_INPUT/FAILED/BLOCKED, max 30 answers (`:101-104`); pushes to `conversation` and `messages`, clears `pending`, sets RUNNING.
- `advance` while RUNNING: if `job.pending` exists, execute it and push a step (`:106-112`); otherwise plan the next action (`:113-157`).
- Any thrown error → `FAILED` with a user-facing message (`:160-163`); `pending` is **not** cleared on failure, so `resume` retries the same pending action with the same key.
- DB `status` column is `COMPLETED` only on completion, else `PENDING` (`:166`); FAILED/BLOCKED/PAUSED rows stay `PENDING` forever (no cancel action exists; no `schoolAiRequest.deleteMany` found under `src/lib` or `src/app/api/cron`).

## 2. The planning step: two-call select→act loop (`service.ts:120-157`)

Per planning step (no pending action):
1. Re-check questionnaire version if the job is questionnaire-driven (`:116-119`).
2. Rebuild the catalog + live context (`automaticCatalog`, `:120`) and check one AI credit is available (`:121`).
3. Build `baseContext = { role, purpose, request, answers, completed: job.steps, previousError, liveContext, tools: Object.keys(catalog.tools), allowedOperations, language }` (`:123`).
4. **Call 1 (select)**: `generate({ system: "Choose only the next tool needed ...", prompt: masked JSON of baseContext + selection JSON schema, maxTokens 800, temperature 0, timeout 12 s })` (`:125-127`). Output must parse as `automaticSelectionSchema` (`schema.ts:39-44`): `select{tool, operation?} | ask | complete | unsupported`. Selected tool must be `in catalog.tools`, and a `school.*` operation must be in `catalog.operations` (`:129`), else 403 → FAILED.
5. **Call 2 (act)** only when type is `select`: prompt = baseContext + `selected` + `responseSchema` = the full decision schema trimmed to that single tool and (for `school.*`) that single operation (`src/lib/automation/output-schema.ts:4-19`; system prompt at `service.ts:132`, maxTokens 6000, temperature 0.1, timeout 45 s). If `ask/complete/unsupported`, the selection result is reused verbatim (`:132`).
6. Zod-validate as `automaticDecisionSchema` (`schema.ts:25-30`); on schema failure one **repair** call (temperature 0, 4000 tokens, 25 s) (`:135-140`); second failure → 422 FAILED (`:141`).
7. Re-authorize the actor (`:143`), re-check questionnaire (`:144-147`), record usage (`:148`).
8. Decision handling (`:149-156`): `act` → `validateSelectedAction` (tool/operation must equal the selection; `validation.ts:5-9`), tool must still be in the catalog, **`evidenceQuote` must be a verbatim substring of `job.request` or any answer** (`:152`), then `job.pending = action; job.pendingKey = "auto-<jobId>-<uuid>"` (`:153`). `ask` → WAITING_INPUT with question. `unsupported` → BLOCKED with reason. `complete` → `validateCompletion` then COMPLETED with `outcome`.
9. `finally`: `version++`, persist the job where `claimToken = token`, release the lease, charge one credit via `consumeAICreditAndLog` only if `usage` was set (`:163-170`).

The pending action is executed on the **next** `advance` (`:106-112`), so every real step is two round trips from the UI: plan, then execute.

What the model is told: tool **names only** (`tools: Object.keys(catalog.tools)`, `:123`) and operation **names only** (`allowedOperations`). The descriptions written in `catalog.ts:32,36,42,43` and the `effect` strings in `src/lib/school-ai/execution.ts:33-49` are never included in any prompt; the only semantic hints are two sentences in the selection system prompt (`:127`: "Classes are created with school.execute operation academics.setup_year. Students use students.create."). The `proposals` array attached to `school.execute` in `catalog.ts:44` is also never sent (only the trimmed decision schema is).

Model transport: `generateAIDraft` → `completeChat` → provider loop (`src/lib/ai/openai.ts:587-621, 374-408`); OpenAI call is plain chat completions with `max_completion_tokens`/`temperature` (`src/lib/ai/openai-settings.ts:12-17`), **no `response_format`/JSON mode**. SDK-level timeout is `AI_TIMEOUT_MS` (default 20 s, `openai.ts:48`) in addition to the caller's AbortSignal. `parseModelJson` strips code fences then `JSON.parse` (`src/lib/school-ai/intake.ts:79-83`); a JSON syntax error is thrown outside the repair path (`service.ts:128,134`) and lands in the generic catch → FAILED, with no repair attempt.

## 5. Bounds, concurrency, worker, UI

- **30-step bound**: planning refuses once `job.steps.length >= 30` and sets PAUSED with a message (`service.ts:114`); answers are capped at 30 (`:102`); UI disables pause/resume at 30 steps (`automatic-workspace.tsx:57`). No continuation mechanism; a new job starts with empty `steps`/`conversation` (`:52`) and the prompt only contains the current job (`:123`) — **no memory across jobs**.
- **Lease/claim**: `advance` reads the row, rejects if `version` mismatches (409, `:92`), **returns the stale job silently if a lease is live** (`:93`), then claims with `updateMany(where reply = <same JSON> AND lease null/expired) set claimToken, lease = now+120 s` (`:94-95`). Persist requires `claimToken = token` else 409 (`:166-167`). The claim therefore uses the full `reply` JSON as the CAS value.
- **Worker sweep**: `sweepAutomaticJobs(db, limit = 4)` every 5 s from the outbox worker (`outbox-worker.ts:46-49`), one sweep in flight at a time; selects `AUTOMATIC_SETUP_V1` rows with `status='PENDING'`, `reply->>'status'='RUNNING'`, expired/null lease (`worker.ts:9-15`); re-resolves the actor via `resolveWorkerPrincipal` (role + accessVersion must match, `access.ts:97-103`) and marks the job FAILED "Your access changed" if not (`worker.ts:18-21`); otherwise calls the same `advanceAutomaticJob` (`:23`). Test `:81-91`.
- **UI polling**: after any state change, when the modal is open, not busy, no local error and `job.status === "RUNNING"`, a 600 ms timer posts `advance` (`automatic-workspace.tsx:54`). On 409 it reloads the job list and adopts the current job (`:47-49`). The pending action's title is shown for the ~600 ms before it runs (`:57`); there is no confirm button. **Tab close**: nothing is sent; `useUnsavedGuard` only prompts when the request/answer textarea has text (`:28`, `src/lib/hooks/use-unsaved-guard.ts:19-29`). A RUNNING job continues via the worker once its lease (if any) expires; with no worker process it waits until the job is reopened from "Saved work" (GET returns the last 20 jobs, `service.ts:36`).
- **Timeouts**: advance route `maxDuration = 60` while the step's provider timeouts sum to 12+45+25 s (`service.ts:127,132,137`) and the lease is 120 s; a killed invocation leaves the browser spinning on the silent lease return for up to 2 minutes.
- **Credits/billing**: one `ensureAICreditsAvailable` check (`:121`) and one `consumeAICreditAndLog` charge (1 credit, token sum of 2–3 calls) per planning step (`:148,168`); charge happens only if the step reached `:148`, so parse/repair failures are unbilled.
- **Live-context caps**: classes/teachers/rooms 200, periods 100, cycles 20 (`catalog.ts:48-56`), told to the model via `catalogLimits`; `school.inspect` caps 500 per kind with a `truncated` flag.

## 6. Validation gates

- `validateSelectedAction` (`validation.ts:5-9`): call 2 cannot change the tool or operation chosen in call 1 (test `:155-162`).
- **`evidenceQuote`** (`service.ts:152`): plain `String.includes` of the quote against `job.request` and each answer. `job.request` is the user's text **plus** the server-appended role interview (`:42`) and/or `"\nConfirmed questionnaire answers:\n" + JSON.stringify(...)` (`:48`). No normalization, no language handling, no paraphrase tolerance. A quote lifted from the appended interview text ("Create records in dependency order using only supplied facts") or from the UI's canned setup sentence (`automatic-workspace.tsx:33`) satisfies the gate.
- `validateCompletion` (`validation.ts:12-17`): `executed` needs at least one step that is neither a read (`school.inspect`, `platform.inspect`) nor a plan (`personal.save_plan`, `work.save`); `plan_saved` needs a plan step; `answered` forbids any non-read step. Tested at `tests/automation/validation.test.ts:8-15` and `execution.database.test.ts:139-154`.
- **"unsupported"** means: the model found no listed tool for the request (`:127` instructs it to say so rather than fake a plan or claim it is forbidden). It sets `BLOCKED` with the free-text reason in `job.error` (`:155`); the UI shows it like a failure with an answer box, and an answer returns the job to RUNNING (`:101-104`, test `:132-138`). Nothing structured is recorded about which feature was missing.

## 7. PII masking (`service.ts:122-132`, `src/lib/ai/pseudonymize.ts`)

A per-step `Pseudonymizer` registers the actor's email and full name, then `maskObject(catalog.context)` and `maskObject(job.steps)` are called for their side effect of registering every string under a sensitive key (`pseudonymize.ts:114-133`, keys at `:34-42`); the serialized prompt is then `mask()`ed by global split/join of every registered value (`:77-84`), and `scanForPII` adds regex hits (emails, phones, national IDs, IBANs) as `ID` tokens (`:162-169`). Model output is `unmaskObject`ed (`:97-107`). Consequences verified in code:
- Keys named exactly `name` are classified PERSON (`:37`), so **class names (`catalog.ts:50`) and subject names (`caps.subjects`) are tokenized as `[PERSON_n]`** and replaced everywhere in the prompt, including inside the user's request; a very short class name (e.g. "1" or "A") would be replaced wherever that substring occurs in the JSON prompt.
- Free-text person names typed by the user are not masked (only regex-detectable identifiers are).
- `school.inspect` receipts store entities whose person names live under `label` (`assistant-catalog-service.ts:38,43,51,58`), which is not a sensitive key; `maskAssistantCatalog` (`:92-96`) exists but automation does not call it (`service.ts:68-69`). Those labels are re-sent unmasked as `completed` steps in every later prompt of the job (teacher names are caught only when the same string also appears in `catalog.context.teachers`, which requires `setup.apply_changes`).

## Findings
- [blocker] **Coverage: 12 tool names + 15 operations, and six roles get no operational tool at all** — The catalog is a hand-written flat object (catalog.ts:28-57). Operational capability comes only from school.execute's 15 typed operations, whose allow-list returns an empty set for SUPER_ADMIN, TEACHER, LIBRARIAN, RECEPTIONIST, STUDENT and PARENT (access.ts:70-77). TEACHER therefore cannot record attendance, enter marks or save a lesson plan through automation; STUDENT/PARENT can only change profile fields or save a private plan; LIBRARIAN and RECEPTIONIST get one create-only tool each. Against the stated goal (any permitted action for any of 11 roles) the gap is structural, not incremental: each new tool needs a schema entry (schema.ts:10-23), a catalog gate, an adapter branch (role-action-service.ts:13-51) and a completion-class entry (validation.ts:13-14). For scale reference the app has 445 route.ts files under src/app/api. _(src/lib/automation/catalog.ts:28-57; src/lib/school-ai/access.ts:70-89; src/lib/automation/schema.ts:10-23; src/lib/automation/role-action-service.ts:13-51; tests/automation/execution.database.test.ts:54-64)_
- [major] **Tool and operation descriptions never reach the model; it chooses from bare names** — baseContext sends tools: Object.keys(catalog.tools) and allowedOperations as name strings only (service.ts:123). The descriptions in catalog.ts:32,36,42,43, the proposals list at catalog.ts:44 and the effect/permission strings in execution.ts:33-49 are used nowhere in a prompt. The only semantics are two sentences in the selection system prompt (service.ts:127). This already causes the prompt to need special hints and will not scale past a handful of tools; a catalog-driven description/retrieval layer is missing. _(src/lib/automation/service.ts:123,127; src/lib/automation/catalog.ts:32,36,42-44; src/lib/school-ai/execution.ts:33-49)_
- [major] **One action per planning step, no plan object, no dependency model, no cross-step transaction** — Each planning step issues two model calls and yields at most one action (system prompt: "Choose one next action at a time", service.ts:132); dependency ordering is left to the model plus the text "Create records in dependency order" in ROLE_SETUP_INTERVIEW (role-setup.ts:5-6). The only mechanism is that live context is re-queried before every step (catalog.ts:48-56). There is no persisted plan, no DAG, no rollback of earlier steps when a later one fails, and the whole job is capped at 30 steps (service.ts:114) and 30 answers (:102). A campus setup (year, classes, subjects, staff, students, timetable, fees) must fit in 30 actions and ~60+ model calls. _(src/lib/automation/service.ts:102,114,123,132; src/lib/automation/role-setup.ts:5-6; src/lib/automation/catalog.ts:48-56)_
- [major] **No dry-run preview and no per-tool confirmation class; everything auto-executes on a 600 ms timer** — previewSchoolAiExecution is called only to obtain previewHash and its content is discarded (service.ts:82-83). All 12 tools are handled identically at decision time (service.ts:149-153); the only guidance about destructive/communication/access actions is prose in the system prompt (service.ts:132), not code. The UI shows the pending title for ~600 ms and then posts advance (automatic-workspace.tsx:54,57). communications.queue_announcement (guardian emails), platform.update_institution and fees.generate_invoices run under the same path as profile.update. _(src/lib/automation/service.ts:82-83,132,149-153; src/components/automation/automatic-workspace.tsx:54,57)_
- [major] **evidenceQuote gate is both brittle and weak: exact substring over a string that includes server-added text** — The check is [job.request, ...job.messages].some(t => t.includes(quote)) (service.ts:152). job.request includes the appended ROLE_SETUP_INTERVIEW text (service.ts:42) and the JSON.stringify of questionnaire answers (service.ts:48), so a quote of interview wording or of the UI's canned setup sentence (automatic-workspace.tsx:33) passes although the user never typed it. Conversely any paraphrase, whitespace/Unicode difference, a quote spanning JSON-escaped characters (newlines become \n, quotes become \"), or a translated quote in ar/ur fails the step with "not supported by your request". No normalization is applied. Test :113-120 only covers a mismatched quote. _(src/lib/automation/service.ts:42,48,152; src/components/automation/automatic-workspace.tsx:33; tests/automation/execution.database.test.ts:113-120)_
- [major] **Over-masking: class and subject names are tokenized as [PERSON_n] and replaced globally in the prompt** — maskObject classifies any key named exactly "name" as PERSON (pseudonymize.ts:37); catalog.context.classes and caps.subjects carry a name key (catalog.ts:50-51,56). Registered values are then replaced by split/join everywhere in the serialized prompt (pseudonymize.ts:77-84), including inside the user's own request. The model reasons about "[PERSON_7]" instead of "Grade 1"/"Mathematics"; a one- or two-character class name would corrupt unrelated numbers, IDs and JSON in the prompt. # B.typedOps

## 0. How `school.execute` actually runs (the pipeline every operation shares)

**Entry (automation engine).** `src/lib/automation/service.ts:61-85` `execute()`:
1. `automaticCatalog(user, job.campusId)` must list the tool; for `school.execute` the proposal's `operation` must be in `catalog.operations` (`service.ts:74-75`, error "belongs to another role or assigned lead").
2. `createWorkspaceRecord(user, { kind: "WORKFLOW" | "CURRICULUM", title, campusId, idempotencyKey: pendingKey, data })` (`service.ts:77`) – data is `workflowDataSchema` (`src/lib/school-ai/schemas.ts:59-71`): `goal`, `steps[≤30]{id,title,status proposed|blocked|ready,module?}`, `sourceIds[≤40]`, `missingInformation[≤50]`, `proposal` (union of the 8 proposal schemas, `schemas.ts:66`), no `subjectId/classId` beside a proposal (`:70`).
3. Self-approval: `updateWorkspaceRecord(..., { action: "approve" })` (`service.ts:81`). Approval runs `assertApprovalRole(user, operation)` and `assertApprovalSeparation(...)` (`src/lib/school-ai/repository.ts:366-369`) plus `approvalIssues` → for WORKFLOW: `missingInformation` must be empty, ≥1 step, no `blocked` step (`src/lib/school-ai/workflows.ts:73-79`). Separation of duties comes from the campus Delivery Policy; platform default is `separationOfDuties: "NOT_REQUIRED"` (`src/lib/school-ai/delivery-policy.ts:197, 252-262`), so self-approval passes unless a school policy sets REQUIRED (then `APPROVAL_SEPARATION_REQUIRED`, `src/lib/school-ai/access.ts:191-200`).
4. `previewSchoolAiExecution` then `executeSchoolAiTool({operation, version, previewHash, idempotencyKey: pendingKey})` (`service.ts:82-83`).

**Registry.** 15 typed operations: `src/lib/school-ai/operations.ts:2` and `src/lib/school-ai/execution.ts:33-49` (`SCHOOL_AI_TOOLS`: kind WORKFLOW for all except `curriculum.import_topics` = CURRICULUM; all `requiresApprovedVersion: true`). The run-queue (`src/lib/school-ai/run-service.ts:103-121`) executes the same registry with key `run-{id}-{step}`.

**Single authorization choke point** `execution.ts:137-145` `authorize()`: (a) `assertApprovalRole` – manager roles SUPER_ADMIN/CAMPUS_ADMIN/ADMIN/PRINCIPAL, or ACCOUNTANT only for the two finance ops (`access.ts:155-158`); (b) `ai.edit` permission + staff role + campus (`access.ts:118-121, 47-50`); (c) seat allow-list `allowedSchoolAiOperations(user, user.campusId)` (`access.ts:84-89`); (d) permission-matrix check `hasMatrixToolPermission` (`execution.ts:115-128`); (e) `assertSchoolOperational` (billing).

**Record gate** `approvedRecord()` `execution.ts:152-159`: record in caller's campus (SUPER_ADMIN any), has campusId, `kind` matches the op, `status === "APPROVED"`, `version` matches, `approvedById` set.

**Idempotency (common to all 15)** `execution.ts:236-254`: `schoolAiExecution` looked up by `(schoolId, requestedById, idempotencyKey)`; same key with different record/version/op/previewHash → 409 `EXECUTION_KEY_CONFLICT` (`:248`); otherwise replay by `(schoolId, recordId, recordVersion, operation)` – one effect per approved version (`:251`). Preview hash recomputed inside the serializable transaction; mismatch → 409 `STALE_EXECUTION_PREVIEW`. Transactions are Serializable with up to 7 retries on 40001/40P01 (`src/lib/school-ai/transaction.ts:13-39`); P2002/P2034 fall back to replay (`execution.ts:337-341`). Every execution writes `schoolAiExecution` + `auditLog("school_ai_executions")`.

**Automation job limits** (`service.ts`): 30 executed steps per job (`:114`), 30 answers (`:102`), evidence quote must appear verbatim in request/answers (`:152`), two model calls per step (select then draft), access version re-checked before each step (`:29-34, 143`).

## Findings
- [major] **Automation self-approval conflicts with separation-of-duties gates** — service.ts approves the record it just created with the same actor (service.ts:81). repository.ts:367-368 runs assertApprovalSeparation against the campus Delivery Policy; the platform default is NOT_REQUIRED so it passes today, but any school whose approved Delivery Policy sets separationOfDuties REQUIRED will get APPROVAL_SEPARATION_REQUIRED on every school.execute step. Independently, finance.apply_operation REFUND fails with FINANCE_SEPARATE_APPROVER when school.correctionSeparateApprover is on, because author === approvedById. _(src/lib/automation/service.ts:81; src/lib/school-ai/repository.ts:366-369; src/lib/school-ai/access.ts:184-200; src/lib/school-ai/delivery-policy.ts:197,252-262; src/lib/school-ai/finance-operations-service.ts:94-98)_
- [major] **Onboarding order crosses seats: operator creates the year, only the academic lead can activate it** — academics.setup_year (OPERATOR_TOOLS) leaves a new cycle DRAFT; academics.transition_year is in ACADEMIC_TOOLS, which an ADMIN/CAMPUS_ADMIN holds only while the campus has no active PRINCIPAL. SUBJECTS, TEACHER_ALLOCATIONS and HOLIDAYS in setup.apply_changes require the class year to be an ACTIVE cycle, so on a campus with a principal the admin's single-run setup stalls after classes are created. _(src/lib/school-ai/access.ts:56,60,73-75,88; src/lib/school-ai/academic-setup-service.ts:58; src/lib/school-ai/school-setup-academics.ts:28,54)_
- [minor] **PRINCIPAL cannot run communications.queue_announcement with default permissions** — The allow-list grants the principal the announcement tool, but the matrix check requires students.view+edit and the PRINCIPAL default matrix has students.canEdit=false, so the tool is filtered out of capabilities and refused in authorize() unless the school grants an override. _(src/lib/school-ai/access.ts:62,349; src/lib/school-ai/execution.ts:126; src/lib/permissions.ts PRINCIPAL block (students canEdit false))_
- [major] **No typed operation creates fee structures, students, staff accounts, bank/chart accounts or attendance rules** — fees.generate_invoices needs existing feeGroup/feeGroupAssignment/lines; setup STAFF only writes pending staffInvitation rows for four roles; students are created only through the separate students.create tool (ADMIN/CAMPUS_ADMIN); there is no attendance-policy operation. - [info] **fees.generate_invoices refuses campuses with an active tax package** — applyFeeInvoices throws FEE_TAX_PACKAGE when activationFor(...) reports an approved invoice tax package, directing users to the Fees module instead. _(src/lib/school-ai/fee-invoices-service.ts:113)_

## Gaps in the permission model (nav features with no module) and modules without a surface

**Features that exist only as capability keys or with no gate at all (outside the 17-module matrix):** Messages (`/messages`, every console); Record/mark/payment corrections (`/corrections`, key `corrections`); Care & safeguarding (`/care`, `careMember`); Service desk (`/service-desk`, `serviceAgent`); Activities (`/activities`, `activityStaff`; parent copy ungated); Today's trip (`/transport`, `tripToday`); Improvement evidence (`/improvement`, `improvementLead`); Canteen (`pkgCanteen`); Pickup on the admin console (`campusOps`, l.177) — while the receptionist's Pickup is `front-desk` (l.334) and `moduleForView` maps `pickup → front-desk` (`src/lib/navigation/modules.ts:35`); Approvals, People & access (including the permissions editor), Billing & plan, Settings / School settings / Campus setup (institutionAuthority / billing / campusOps); Group standards (groupConsole); Guardians & access needs `students` + campusOps; Learning actions (admin: `academicLead`; principal: **ungated** l.234); Academic year on the principal console (**ungated** l.237, whereas the admin copy is gated by `students` l.162); Exam Studio / My online exams (`schoolAiExams`); Access plans for TEACHER/PARENT/STUDENT (`accessPlans`); Meet a teacher (parent, ungated); Study help and Portfolio & goals (student, ungated); the entire APP_OWNER console (platform operations have no module at all). For the AI engine this means permission snapshots alone cannot authorise these features; each needs its own predicate (the ones in (b)) carried into the adapter.

**Modules with no nav surface:** every module has at least one row somewhere, but coverage is uneven. `accounts` appears only on the ACCOUNTANT console (l.312) although ADMIN/CAMPUS_ADMIN hold VAED by default; `transport`, `inventory`, `dormitory` appear only on the admin console; `payroll` only on admin (approvals) and accountant (prepare); `admissions` only on admin and receptionist; `library` on librarian and admin-as-fallback-desk; `front-desk` on receptionist and admin. Roles granted a module view with no row for it on their console: ACCOUNTANT (`students`, `staff`, `attendance`), LIBRARIAN (`students`, `reports`), RECEPTIONIST (`students`, `timetable`, `attendance`, `reports`), PRINCIPAL (`leave` only as a hidden view plus My leave), TEACHER (`leave` only via the account menu). These are read grants the AI may legitimately use for look-ups (e.g. a receptionist finding a student) even though the sidebar shows nothing.

**Automation coverage against this checklist (the practical gap for Flagship 1):** the executable allow-list grants zero `school.execute` operations to SUPER_ADMIN, TEACHER, LIBRARIAN, RECEPTIONIST, STUDENT, PARENT and APP_OWNER (`access.ts:70-77`), so for those roles the engine can only run the role tools in the catalogue (campus.create; library.create_books; front_desk.log_call; profile/plan). ## Findings
- [major] **Executable AI coverage is a small fraction of each role's navigation checklist** — The seat allow-list `schoolAiOperationsFor` returns an empty set for SUPER_ADMIN, TEACHER, LIBRARIAN, RECEPTIONIST, STUDENT, PARENT and APP_OWNER, so `school.execute` is never offered to them (catalog.ts only adds it when `caps.tools` is non-empty). Their only mutations are the handful of role tools in `automaticCatalog`. Even the four roles with operations (PRINCIPAL 9, ACCOUNTANT 2, operators 6-15) cover a minority of their nav rows: no attendance/marks/homework for teachers, no visitors/pickup/admissions/complaints/post/certificates for receptionists, no lending for librarians, no payments/receipts/reminders/tax/payroll-prep for accountants, no admissions/guardians/staff invites/leave or payroll approvals/transport/hostel/inventory/canteen for operators, no delegation/approvals/standards for the group admin. Flagship 1 ('execute it if that role has that feature') needs one typed adapter per nav feature per role beyond the current 15 operations + 7 role tools. _(src/lib/school-ai/access.ts:70-77 (allow-list; l.76 `return new Set()`), src/lib/automation/catalog.ts:28-45 (tools per role), src/lib/navigation/role-nav.ts:262-411 (teacher/accountant/receptionist/librarian/parent/student leaves))_
- [major] **Many nav features are gated by capability keys or nothing, not by any of the 17 permission modules** — Messages, corrections, care, service desk, activities, trips, improvement evidence, canteen, admin pickup, approvals, people & access, billing, settings/campus setup, group standards, learning actions, Exam Studio and the whole APP_OWNER console are gated by `CapabilityKey`s or shown unconditionally. A permission snapshot (`loadWorkspacePermissionSnapshot`) therefore cannot authorise these; each adapter must carry the matching predicate from scope.ts/capabilities.ts (e.g. `canLeadAcademics`, `isInstitutionAuthority`, `canOwnSubscription`, the duty queries). _(src/lib/navigation/role-nav.ts:119-124, 145, 163, 172, 177, 180, 183-193, 217, 234, 237, 247-248, 290-295, 319, 375-382, 395-407, 414-437; src/lib/navigation/capability-keys.ts:3-11; src/lib/navigation/modules.ts:36-37)_
- [minor] **PRINCIPAL 'Learning actions' and 'Academic year' leaves have no visibility clause** — Both principal leaves are always visible regardless of permissions, while the admin console gates the same views by `academicLead` and `students` respectively. Not a security hole (APIs keep their own gates) but the nav is the product's own 'features for this role' list and is inconsistent here. _(src/lib/navigation/role-nav.ts:234 and :237 (no `visible`), versus :145 and :162)_
- [minor] **Admin 'Pickup' is gated by campusOps, receptionist 'Pickup' by the front-desk module** — The two consoles gate the same view differently, and `moduleForView('pickup')` maps it to `front-desk`. An operator whose school revoked front-desk view would still see Pickup on the admin console. _(src/lib/navigation/role-nav.ts:177 vs :334; src/lib/navigation/modules.ts:35)_
- [minor] **V2 cut-over date is three days in the future, so a deliberate grant equal to the V1 default is currently discarded** — `ROLE_DEFAULTS_V2_EFFECTIVE` is 2026-10-26. Until then `isLegacyDefaultRow` treats any stored row whose flags equal the V1 default for that role/module as 'not customised' and `moduleFlags` returns the V2 default instead. Example: granting PRINCIPAL `fees` VAED or RECEPTIONIST `fees` VA.. today has no effect. The comment says the orchestrator sets the real date at integration; worth confirming before relying on edited grants in QA. _(src/lib/permissions.ts:283, 308-314, 321)_
- [minor] **canManageLibrary / canManageFrontDesk admit PRINCIPAL although PRINCIPAL's default has no library or front-desk flags** — Both predicates are built on the deprecated `canManageOperations` (= `canManageAcademics`), which includes PRINCIPAL. A route that relies on the predicate without the paired `assertPermission` would admit a principal to library/front-desk writes. The file's own rule says the matrix is checked beside the predicate, so this is a consistency note for adapter authors rather than a confirmed hole; the 10 + 8 call sites were not audited. _(src/lib/api/scope.ts:219-226, 260-266; src/lib/permissions.ts:213-214)_
- [info] **Roles hold module view grants that have no row on their console** — ACCOUNTANT (students, staff, attendance), LIBRARIAN (students, reports), RECEPTIONIST (students, timetable, attendance, reports) are granted view with no leaf. ADMIN/CAMPUS_ADMIN hold `accounts` VAED with no accounts leaf (only the accountant console has one). The AI may use these read grants for look-ups; the nav list alone understates what the role may read. _(src/lib/permissions.ts:222-278; src/lib/navigation/role-nav.ts:169-173 (admin Money group has no accounts leaf), 303-362)_
- [info] **Families reach /ai through a different gate than staff** — `capabilitiesFor.schoolAi` admits PARENT/STUDENT with `ai.canView`; `/ai/page.tsx` sends APP_OWNER/STUDENT/PARENT to the personal `AutomaticWorkspace` (gate `ai.view`, none for owner) and staff to `SchoolAIWorkspace` behind `assertSchoolAiAccess`, which refuses families. Consistent today, but two gates for one route; an adapter must not assume `assertSchoolAiAccess` for family requests. _(src/lib/navigation/capabilities.ts:142; src/app/ai/page.tsx:18-19, 30; src/lib/school-ai/access.ts:47-50)_

- [blocker] **Most questionnaire answers have no typed adapter: the 'auto-generated system' is only classes, weekends, rooms/periods, subjects, staff invitations and students** — Of the 18 answer keys, only grades (academics.setup_year), workingDays (WEEKENDS), resources (ROOMS/PERIODS), curriculum→subjects (SUBJECTS), staff (STAFF invitations) and students (students.create) can produce records. schoolName, country, timezone, campuses, feePolicy, assessmentPolicy, communications, migrationSource and firstOutcome are prompt context only; language/currency/module enablement are not asked and have no tool. - [major] **Academic year is collected twice: the wizard already created an ACTIVE cycle, and the questionnaire's free-text academicYear/startDate/endDate can only KEEP it on an exact label/date match** — completeSetup upserts an ACTIVE AcademicCycle from sessionLabel/sessionStart/sessionEnd. academics.setup_year refuses a different label or dates (CYCLE_DETAILS_CONFLICT) and refuses any other year while one is ACTIVE (ACTIVE_CYCLE_CONFLICT). ## B. Decisions in tension with "the AI executes anything the role can do", and how to reconcile each

**T1. Self-approval and headless execution vs. "explicit review" (rules 3, 4, 5).** Today the automation engine creates the workspace record and immediately approves it on the requester's behalf (`service.ts:79-81`: "The user's explicit execution request authorizes eligible actions"), previews, and executes. The pending action is executed on the *next* advance with no confirmation step: the UI auto-advances every 600 ms while RUNNING (`src/components/automation/automatic-workspace.tsx:54`) and the outbox worker advances RUNNING jobs without a browser (`worker.ts:12-13,23`, `service.ts:105-112`). The only authorizations are the catalog membership, the `evidenceQuote` (`service.ts:152`) and the domain services' own checks. This collides with `prd-revised.md:164/349` and `ROLLOUT.md:13`.
*Reconcile:* give every typed tool/operation a static **confirmation class** in the registry (a field beside `kind`/`permission` in `SCHOOL_AI_TOOLS` and in `automaticCatalog`, never model-chosen):
- **Class A — auto-run** (keeps today's behaviour): reads (`school.inspect`, `platform.inspect`), own profile, private plans, and low-blast-radius creates already protected by domain validators and replay (`library.create_books`, `front_desk.log_call`, `curriculum.import_topics` which only appends).
- **Class B — confirm-in-chat**: school-structure creates with no money, publication or outbound message (`students.create`, `campus.create`, `academics.setup_year`, `setup.apply_changes`, `timetable.create_draft`, `timetable.create_school_drafts`, `exams.create_session_plan`). The job enters a new `WAITING_CONFIRM` state holding the exact preview; the confirm call carries `pendingKey + previewHash + job.version`; the worker never advances a `WAITING_CONFIRM` job; a bare "yes" in text or voice without that binding does nothing (`ROLLOUT.md:13`).
- **Class C — route-to-domain-approval**: everything in the `prd-revised.md:164` list — `finance.apply_operation`, `fees.generate_invoices`, `communications.queue_announcement`, `timetable.publish_reviewed`, `students.promote_enrollment`, `academics.transition_year`, `attendance.record_register`, `operations.record_risk_decision`. The AI saves the draft and preview, does **not** self-approve, and completes with a new outcome `awaiting_approval` (extend `validateCompletion`), linking to the Work/approval surface; where `assertApprovalSeparation` requires a second actor the message names that, instead of the job failing. Keep `repository.ts:366-368` as the enforcement point so a school with `separationOfDuties: REQUIRED` can never be self-approved from chat.

## Risk notes
- PII policy (memory: pseudonymize before any prompt). service.ts:122-126 masks only the actor's own email and fullName plus scanForPII hits. catalog.ts:48-56 puts teacher fullNames (teachers list, up to 200), the actor profile and class names into liveContext, and students.create carries learner and guardian names. Those names reach OpenAI unmasked unless scanForPII catches them; the decisions reader's 'unproven' finding is supported by this code.
- AI credits and rate limits. /api/automation POST limits to 10 starts per 5 min per user (route.ts:8), but advance steps (up to 30 per job, automatic-workspace.tsx:57) each make 2-3 model calls (selection, act, repair at service.ts:127-137), and consumeAICreditAndLog runs once per step (:168). The plan needs per-action credit pricing and a per-job budget, with onboarding (many steps) checked against plan aiCredits (openai.ts:509,545) before starting. Otherwise a school runs out of credits mid-provisioning and is left half set up.
- Tenant guard: platform.ts:9 uses runUnscoped for APP_OWNER updates. Any new owner or group-console adapter (cross-campus SUPER_ADMIN, provisioning) must be enumerated and audited, and gen-tenant-registry rerun after schema changes (memory).
- Notification and communication side effects of reused services were not catalogued: insights/route.ts:447 creates a parentConversation, invite.ts notify(STAFF_INVITED), reports.send_all, digests, whatsapp, and timetable.notify_version. The prompt rule 'ask before sending communications' (service.ts:132) is prompt-only; tools need a declared sideEffects field.
- Idempotency: the engine keys each step by pendingKey, but several adapters are not idempotent (C1 promote_students; C4 correction requests; C6 inventory key reuse without a request hash; GET handlers that write, e.g. /api/auth/verify, learning-transfers export, notifications listInbox, library desk, principal queue). Retries from the worker could double-apply.
- Audit: role-action-service.ts:53 writes a generic 'automatic_action' audit row. Reused services may also audit, or may not (inline-prisma routes often do not). The plan must define one actor and source attribution (AUTOMATIC) per write and keep human approvals (separation of duties) out of AI self-approval. updateWorkspaceRecord auto-approve SoD was not verified (ui reader).
- Locale/RTL/i18n: automatic-workspace.tsx uses inline ar/ur ternaries (lines 55-56) and dir=rtl for any non-English language, rather than the shared i18n catalog. Adding languages or tool-specific prompts will not scale. The design-system gate (check:ui) and mobile layout of the fullscreen modal are unverified.
- ROLE_DEFAULTS_V2_EFFECTIVE = 2026-10-26 (permissions.ts:283) is three days away. Tool exposure computed from loadWorkspacePermissionSnapshot will shift for schools with legacy rows at cut-over, so tests must cover both sides.
- Stale-session dead-end (memory): a deleted school yields 'Operations Locked'. Worker jobs re-resolve the principal (worker.ts:19) and fail, but an onboarding job interrupted by plan or billing state (requireAuthUser rejects non-operational schools) has no resume or rollback story.
- The orphan saveMarks server action (marks.ts:15) and the invite.ts server actions skip route-level checks. Adapters must reuse the route-level service, not these actions.

## Verdict
The inventory is not complete enough for the stated goal. Walking the top-level dirs under src/app/api shows three write dirs that no cluster inventoried. The largest is src/app/api/school-ai, with about 80 write routes covering Exam Studio, online exams, setup generation, intake, runs and conversations. The other two are src/app/api/ai (generate-remarks, review and insights, which write report cards and parent conversations) and src/app/api/automation, the engine's own endpoints. As a result, the TEACHER tests/AI, STUDENT online exams, Exam Studio and secure exam-delivery nav features have no inventoried capability.

Feature 2 has two further problems. First, there are three competing onboarding pipelines that no one reconciled: the onboarding/setup-service wizard, the automation ONBOARDING questionnaire (ADMIN/CAMPUS_ADMIN only, service.ts:44) and school-ai setup-generation. Second, the current design always defers roster, curriculum and fees/payroll (setup-state.ts:250-253). That contradicts "fully provisions".

The readers also missed several cross-cutting concerns:
- PII: teacher names in liveContext go to the model unmasked.
- Credits: there is no per-job credit budget for multi-step onboarding.
- Confirmation: there is no server-enforced confirmation class for destructive, financial, access and communication tools, because the UI has no approve step.
- Side effects: notification and communication side effects are not declared.
- Background execution: the worker runs only via outbox-worker, and vercel.json has no crons.
- Language: inline ar/ur strings instead of the i18n catalog.

The cluster digests also contradict each other: duplicate ownership across C2/C3/C4/C5/C7, and the role reader's claim that four roles "execute nothing" ignores catalog.ts role tools.

Fix these before finalizing the plan. Deduplicate the keys, add the school-ai/ai/automation clusters, add an "automation tool exists / confirmation class / side effects / credit cost" column per row, and pick a single onboarding pipeline with a dependency-ordered adapter map.
