# Current source audit — administration, family experience and operations

Prepared 15 October 2026. Repository: `/Users/angular_dev_15/Downloads/skoolee-ai`.

This audit reads the current working tree, including pre-existing uncommitted Exam Studio work. It does not modify application code, deploy the application, inspect a production database, or establish that a feature passes an authenticated live journey. **Present** means meaningful source implementation was inspected; **partial** means a subset exists; **not found** means no matching implementation was found in the inspected source, not proof that a connected external service cannot provide it. Test files were inventoried but not executed for this documentation-only audit.

The working tree contains **89 `page.tsx` files, 287 API `route.ts` files and 155 Prisma models** at audit time. These replace the older review's 69/199/107 counts; counts are breadth, not readiness percentages. `AGENTS.md` and the installed Next 16.2.3 page and route-handler guides were read before inspection.

## Product conclusion

The code has a much stronger school administration and control foundation than the 7 October review implies. The principal remaining product gap is the complete, convenient daily loop: evidence → teacher action → learner work → family follow-through → reassessment. The family and student screens are still mainly record viewing, while the AI workspace carries much of the newer assessment capability. Connecting those experiences and proving adoption is more valuable than adding another generic dashboard.

The founder has selected **international schools globally from launch, alongside local Pakistani, Saudi and UAE schools**. Implement a shared product with explicit supported combinations of country, school curriculum, language, payment rails, hosting and regulatory commitments. Language or currency formatting alone does not establish local operational support. Permit schools to adopt the flagship alongside their existing SIS/LMS; do not force migration of payroll, safeguarding, tax invoicing or admissions before an assessment pilot. Existing CSV staging offers a practical initial bridge, but repeatable roster exchange and identity mapping must become launch dependencies.

## Current source findings to append to existing tickets

### SKO-432 / SKO-431 — safe payment recovery and issuance

1. **Production misconfiguration sends families to an unusable simulator.** `src/app/api/fees/pay-online/route.ts:54` checks provider credentials and otherwise returns a `/safepay` URL. `src/app/api/safepay/simulate/route.ts:24` rejects production. The source establishes a dead-end production checkout when configuration is missing; it does not establish a production settlement bypass.
   - UX: payment method availability before Pay; friendly configured alternative; return to the same child/invoice; processing and delayed confirmation states; no real-looking card entry on an unavailable method.
   - Acceptance: production without gateway credentials returns a typed unavailable response before creating an open order; non-PKR shows supported methods; simulator is explicitly development-only at entry and submission.
   - QA: remove gateway config in a production-like test, attempt Pay from parent/student/staff, verify no orphan pending order or card form; restore gateway and retry; replay provider callback and verify one receipt.
2. **Family return route is wrong.** Same route uses `/dashboard/fees` as gateway return for every actor. That layout redirects family roles to their default dashboard, losing fee/invoice context.
   - UX/acceptance: persist a safe role-appropriate return target and invoice ID; confirm status using server state; retain selected sibling and language. QA parent, student, accountant, expired session, cancelled checkout and delayed webhook.
3. **Manual retry idempotency is not explicit.** `src/app/api/fees/collect/route.ts:21` accepts no request idempotency key. `src/lib/fees/payment.ts:29` locks the invoice but records another payment on retry; a null reference is allowed. A lost HTTP response after commit may therefore produce a second collection if retried.
   - Acceptance: stable operation key binds tenant, invoice, actor and request fingerprint; identical retry returns original result; changed amount under same key conflicts; audit/receipt/event happens once. QA inject disconnect immediately after commit, retry from same and second tab, verify one allocation, ledger entry and receipt.
4. **Receipt number sequence is not serialized across invoices.** `src/lib/fees/payment.ts:46` reads latest campus payment then increments; lock is per invoice and `Payment.receiptNo` is not unique in `prisma/schema.prisma:2044`. Two simultaneous collections against different invoices can choose the same number.
   - Acceptance: atomic campus/year sequence and appropriate database uniqueness; preserve historical receipts; clean migration/conflict handling. QA concurrent collections across 20 distinct invoices and same invoice, retries, year boundary and multiple campuses; all receipt identities unique and balances correct.

### SKO-398 — admission configuration and role-grant consistency

The four-step form and lead pipeline are meaningful implementations. Avoid another static admissions rewrite. Add schema-versioned fields, preview for languages and small screens, document checklist and explicit consent fields. Medical details should be optional or policy-governed and access-restricted rather than globally mandatory.

`api/admission-queries` POST follows `admissions.add`; PATCH first requires `canManageOperations` and then `admissions.edit`. Default receptionist edit is false, so default behavior is consistent; a custom grant of edit still cannot authorize that role. Define the intended grant contract and enforce it uniformly. Do not claim cross-campus leakage based only on a route's explicit filter: the Prisma extension also injects campus scope.

Acceptance: permitted staff can take enquiry → log follow-up → convert exactly once; disallowed staff receive a useful reason; no silent lost edits. QA custom receptionist grant/revoke mid-session, duplicate lead/child, conversion double click, invalid dates, stale edit, guardian invite delivery failure, refresh and draft restoration.

### SKO-392 / SKO-444 / SKO-447 — separate presentation support from market support

The current locale selector supports PK, SA, AE, KW and OTHER, even though several more currencies exist. Country support needs an explicit matrix: interface language, school curriculum, timezone/calendar, fee currency, payment availability, tax/e-invoice capability, data region, agreements and service coverage. Do not automatically claim a market is supported when an administrator selects its currency.

Acceptance: a school in a global country can use flagship assessment with a known unsupported finance package clearly disabled; no silent Karachi timezone or USD assumptions after explicit country choice; effective-date changes never rewrite historical invoices/results. QA EN/AR/UR with Arabic RTL, JPY 0 decimals/KWD 3 decimals, daylight-saving and date-only events, country/currency overrides, historical export and mixed-currency group totals.

### SKO-445 / SKO-446 / SKO-397 — global adoption alongside existing systems

Add a first-run decision: **Use Exam Studio with my current school system** or **Set up school operations**. The former asks only for trusted school identity, data processing/region choices, academic context and minimum roster/source mapping. It should not demand payroll, full fee setup, or an entire ERP migration.

Acceptance: external IDs scoped by system/tenant; CSV reconciliation now, standard roster/identity integration through explicit contracts; sync preview, last successful sync and failure ownership; field ownership rules prevent writes back into another system without configuration. QA reimport renamed/moved pupils, duplicate IDs in two source systems, withdrawn student, changed guardian access, interrupted sync, replay events and source rollback. A paid first-class pilot must be possible while existing SIS remains authoritative.

## Release evidence and commercial priorities

The extensive `tests/design-system`, `tests/authorization`, `tests/guardians`, `tests/locale`, `tests/corrections`, `tests/imports`, `tests/report-versions`, `tests/outbox`, `tests/mfa` and `tests/school-ai` directories are valuable assets. Their presence is not a passed test result. Ticket completion must link the checked commit, environment, fixture roles, automated result, browser recording/screenshots, expected versus actual outcome and unresolved limits.

For international-school launch, prioritize: flagship pilot onboarding and SIS coexistence; stable identity/authorization; core assessment → recovery → family loop; secure global configurations; recoverable payment only in explicitly enabled markets; and measurable pilot evidence. Offer other ERP modules as supported optional capabilities rather than requiring them for flagship adoption. Transport, hostel, clinic, payroll and local tax expansion should follow committed buyer needs.

Funding preparation should measure time to first reviewed assessment, weekly active teachers, successful learner completion, teacher correction rate, completion of learning interventions, reassessment coverage, family action completion, onboarding effort, support cost and willingness to pay. A $10 million target is a commercial objective, not a feature acceptance criterion or a promise that software scope can guarantee funding.
